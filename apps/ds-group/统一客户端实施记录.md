## 本轮实现

正常入口先读取公开 `client-config.json`，固定客户端、归属 Core、认证和 Matrix 地址。默认同源配置继续可用。新跨 origin 配置要求显式 HTTPS 或本机 loopback；原有可信 HTTP 同源部署保留，包括私网 HTTP 网页、从其归属服务发现的私网 Matrix 地址及原会话。HTTP 私网页面仍受浏览器安全上下文能力限制，不能因此声称 PWA 或系统推送可用。配置不能携带秘密，也不接受从 URL 参数或外服发现结果重设登录目标。

归属发现按中央身份 v1 契约核对 `authorityId`、Matrix server name、稳定 subject 及完整 Matrix user ID。登录和注销使用固定认证入口，所有业务请求、上传、附件元信息和下载使用固定归属 Core，显式省略 cookie 并拒绝重定向。未知服务器仅接受无凭据公开发现。没有把普通 token 发给外服 Core，也没有新增第二套认证服务。

`ds-group.session` 的旧未绑定会话只在原同源入口迁移。新存储键包含部署绑定、完整人类身份、中央 subject/authority、协作空间和房间。受认证 `/api/me` 确认后的旧身份升级会迁移相同用户的草稿及待确认 transaction ID。切服、切房和退出后的迟到请求分别检查原身份及目标；旧身份发送回执不能清空新身份的编辑内容，结果未知时保留原 transaction ID 供幂等核对。

服务器栏来自 `/api/spaces` 的真实归属 Matrix 加入/邀请事实与本服准入交集，目录来自 `/api/directory`。客户端按完整房间 ID 分组，同名成员显示完整身份以区分来源。`connected` 显示为“可访问”，不表示远端物理在线；受限房间不进入可发送频道。邀请接受及精确房间加入使用归属 Core 的 `join`，拒绝邀请及离开使用 `leave`。支持带服务器后缀的旧房间 ID 与 Matrix v12 的不透明房间 ID。发现成功不创建空间成员资格，加入失败显示服务端拒绝或待确认结果。本轮后端没有持久申请流程，因此没有伪造“申请已批准”。

没有 `/api/spaces` 的旧 Core 只从受认证 `/api/rooms` 建立兼容空间，不从公开 bootstrap 推测加入关系。新中央服务可以没有初始房间，`roomId:null` 时仍可注册首个账号，再从正常界面创建第一个房间。

个人设置只包含账号、外观和通知。“我的 Bot”有独立管理入口，管理对象来自实际 `ownedBots`，远端目录声称的 ownerId 不赋予管理权。身份组保留在归属服务的协作入口，编辑按钮以服务端 `canManage` 为准。运维节点、预算、存储、部署及管理员配置已移出个人设置。邀请按钮只在后端明确提供 `room.permissions.inviteMembers === true` 时显示；当前治理基础接口尚未提供该权限事实的场景会隐藏操作，待主线程对接后启用。

上传改为可取消的 fetch，保留稳定 `X-Upload-Id` 并阻止跨地址重定向；上传中显示待完成状态，成功由真实回执确认。草稿附件、回复及待发消息随原空间保存。附件下载带原消息的完整 roomId 上下文，使用鉴权读取后的 blob URL 预览。普通对话区继续只显示消息附件和轻量三点活动提示，任务历史通过显式窗口打开。

service worker 在客户端 origin 注册，只缓存静态应用壳。API、发现响应、消息和附件不进入离线缓存。通知 owner 绑定只存完整 userId、homeCoreUrl、authorityId，不存 token 或消息。新通知深链必须匹配当前身份、归属及实际房间成员资格；旧后端缺少接收人绑定的推送只显示通用通知并打开主页。实际系统推送送达仍需后端逐接收人元数据和手机验收。
