## 1 当前目标与授权

用户已将项目更名为 **DS-Group**，目标是让多个人类与多个 Bot 像聊天软件中的正式成员一样共同对话和协作。每个 Bot 是一个长期个体，有独立名称、身份、上下文、记忆、任务和工作进度。Bot 可以运行在不同机器，加入共享核心后与人类和其他 Bot 交流。识雨保留为首个 Bot 的名称。

用户明确授权 Codex 开启 Goal 并无人值守推进首个框架，包括源码、必要依赖、构建、运行测试、失败诊断和修复复验。本轮远端模型唯一使用 `opencode-go/deepseek-v4.1-flash`，测试次数不设上限，本机与用户测试机资源可用于实现本轮目标。每次验证仍记录版本、输入、结果、用量可见性和遗留问题。

新产品实施根为 `apps/ds-group/`。现有 `plugins/shiyu/` 保留原识雨内核与未完接手工作，`plugins/shiyu-workbench/` 保留资料工作台，`lab/` 保留并独立升级识雨健身房。当前五人七日剧本及其实施分工继续依据[健身房升级方案](<识雨健身房长程互动升级方案.md>)执行。

## 2 首个框架的工程选型

用户确认了产品目标和自主实施范围。**Matrix/Synapse 真实聊天核心、DS-Bot 节点和 DS-Group 桥接层，是实施代理在该范围内作出的工程选型。** 后续按实际验证结果维护这一基线。

| 部分 | 固定来源或实现位置 | 承担的能力 |
|---|---|---|
| Matrix/Synapse | 官方镜像 `ghcr.io/element-hq/synapse`，版本 `1.164.2` | 人类与 Bot 的聊天账号、房间、成员、消息事件和同步 |
| DS-Bot | `0.2.7`，固定提交 `71d344bf193f3f18185f25de3d8e5c483046910a` | 长期 Bot 身份、DSH Session、记忆、上下文维护和工具工作 |
| DS-Group 核心 | `apps/ds-group/src/` | 节点登记、Bot 映射、桥接与协作关联、状态查询 |
| DSH 节点适配 | `apps/ds-group/dsh-plugin/` | 将外部聊天消息交给本地 DS-Bot，返回回复与结果 |
| 聊天界面 | `apps/ds-group/web/` | 多成员房间、私聊和节点运行状态 |
| 部署与验证脚本 | `apps/ds-group/scripts/`、`apps/ds-group/tests/` | 启停、配置、模块检查及真实链路验证 |

首轮本机 Synapse 使用固定 ARM64 镜像摘要 `sha256:37090b4e5f26171922321a6acd1acf2675cb862f3b0cdf368f0dbbae6a70439a`。后续发行改用同版本多架构 index `sha256:f0df87cff259872637b4b5e5174b9977e5e3046dd421505407803b5e45c5f842`，包含该 ARM64 镜像及 amd64 镜像。两种架构已由原生 GitHub runner 通过部署与持久化检查，见[发行验证](<../apps/ds-group/发行验证.md>)。DS-Bot 供应源码及来源记录位于 `apps/ds-group/vendor/ds-bot/`，版本与修改情况以其中 `UPSTREAM.json` 为准。

DS-Bot 已有 Bot 名称、职责和模型配置，长期记忆与长对话维护，当前复用范围以其固定源码和适配代码为准。它的群聊 Session、状态文件和本地运行时由节点使用，跨机器寻址及聊天核心接入由 DS-Group 补齐。[固定 DS-Bot 源码](https://github.com/Fei2411/DS-Bot/tree/71d344bf193f3f18185f25de3d8e5c483046910a/ds-bot)

## 3 组件职责与状态归属

```text
人类客户端 ─┐
            ├─ Matrix/Synapse 聊天服务
人类客户端 ─┘           │
                       DS-Group 核心与桥接
                       ├─ 节点 A → DSH + 财务 Bot
                       └─ 节点 B → DSH + 人事 Bot
```

| 状态 | 主要保存方 | 核对规则 |
|---|---|---|
| 成员账号、房间、成员关系和公共消息 | Matrix/Synapse | 以聊天事件身份和服务器返回的同步位置核对 |
| Bot 与节点映射、当前节点状态、协作关联 | DS-Group 核心 | Bot 身份与节点运行代次分别记录 |
| Bot 原生 Session、上下文和个人记忆 | 所属 DSH/DS-Bot 节点 | 重启后恢复原 Bot，核对 Session 与记忆引用 |
| 节点收件位置、已处理消息和待回传结果 | 核心与节点按协议分工持久保存 | 区分消息已接纳、Bot 已处理和回复已送达 |
| 工具执行及产物 | 执行节点 | 结果绑定原请求、执行 Bot 和实际产物 |
| 跨 Bot 工作事项 | 核心持有协作关联，执行节点持有执行事实 | 请求者、执行者、原消息和结果保持可追踪关系 |

成员身份采用稳定标识。人类与 Bot 都能被寻址、加入房间、发送消息和接收回复。Bot 的长期身份与机器节点身份分别保存，节点重启的运行代次也单独记录。这样同名成员、Session 换段或节点重连都能保持明确归属。

同一个 Bot 的主消息处理串行，不同 Bot 独立推进并可并行。每条输入保留发送者、房间、事件身份、引用和关联事项。Bot 选择回应、继续任务或等待时，使用自己的上下文与当前事件。跨 Bot 协作通过请求和结果事件衔接，共同讨论保留来源和回复对象。

## 4 跨机器接入需要保持的行为

首个框架采用统一网络接口连接核心与节点。部署位置可以变化，协议中的稳定身份、消息关系和恢复语义继续保持。

1. 节点登记 Bot 身份、节点身份、可用状态和协议版本，核心能展示在线与离线事实。
2. 核心将房间或私聊消息映射到目标 Bot，节点持久记录接收位置，再进入该 Bot 的处理队列。
3. 节点发出的回应保留原始关联，核心记录投递结果，聊天服务返回真实事件身份。
4. 网络中断时保存待处理消息与待回传结果。重连按游标补收，并按原消息身份核对重复投递。
5. 同一 Bot 在恢复前核对活动节点与运行代次，迟到结果继续绑定原任务和原轮次。
6. 任务执行状态、消息送达状态和模型回复状态分别展示，便于处理执行已完成但回复尚未送达的情况。

初版重点验证固定节点的独立运行和恢复。跨机器实测需要记录机器、网络地址、版本、断连过程和恢复结果。后续 Bot 迁移和自动接管另以实际实现与证据登记。

## 6 最小验收

以下按当前首切片证据登记。真人账号由自动化客户端代表发消息，生成来自真实 DS-Bot/DSH 和指定远端模型。

| 编号 | 场景 | 通过条件 | 本文登记状态 |
|---|---|---|---|
| DG-01 | 两个真人身份与两个 Bot 同群 | 四个独立成员均可发送或接收消息，来源、顺序、引用和回复对象可核对。自动化脚本可代表真人账号发消息，测试方式据实标注 | 同机真实通过，两个合成人类账号与两个 Bot |
| DG-02 | 私聊与群聊切换 | 真人可与指定 Bot 私聊，Bot 在多个场合仍保有同一身份，消息返回原目标 | 同机真实通过，群聊/私聊与私聊委派回传 |
| DG-03 | 实例内串行、实例间并行 | 同一 Bot 的主处理区间有序，两个 Bot 的独立处理可重叠。以实际开始与结束事件核对 | 真实通过，含 provider 调用区间重叠 |
| DG-04 | 跨 Bot 委派与结果回传 | 请求形成稳定关联，指定 Bot 执行并返回结果，请求者在原事项中继续回应。结果与产物或执行回执一致 | 限定核算任务通过，逐段 outbox/Matrix 核对 |
| DG-05 | 节点断线与补收 | 离线期间其他成员可继续交流，重连后补齐该节点应处理的消息，重复投递具有可核对的处理结果 | 单节点离线补收及重复发送通过 |
| DG-06 | 节点重启后的 Session 与记忆 | 重启后 Bot 身份和上下文绑定延续，先前写入的事实可在后续生成中正确召回，未完事项可继续 | 原生 Session 与随机事实回忆通过，在途任务续跑待验 |
| DG-07 | 物理跨机器接入 | 核心与至少一个 Bot 节点运行在不同机器，完成登记、群聊、私聊、断线恢复和结果回传 | 待跨机器实测 |

补充产品方向已经接入。人类账号可以拥有多个 Bot，并将自己的 Bot 邀请进群。左侧提供个人 Bot、私聊和服务器空间，外部服务器入口当前用于发现，跨独立服务器的身份与节点映射待实现。前端提供 PWA 安装、离线应用壳、手机/电脑布局和 Web Push 接入。手机实机通知仍需可信 HTTPS 与安装授权后验收。

每项证据记录代码与上游版本、拓扑、账号与 Bot 的合成身份、输入事件、实际回复、状态变化和判定。模型调用使用唯一允许的远端模型，已知用量与未观测部分分别报告。失败先保留原始结果，再记录修复后的新一轮验证。

## 7 实施顺序

1. 建立真实 Matrix/Synapse 聊天服务，验证成员、房间和消息同步。
2. 接入两个隔离 DSH/DS-Bot 节点，固定身份、模型、工作目录与上下文归属。
3. 完成核心桥接、真人聊天入口、群聊与私聊，核对串行和并行区间。
4. 接通跨 Bot 请求与结果返回，验证任务归属和原会话续接。
5. 验证节点断线、核心或节点重启、补收、Session 恢复与记忆召回。
6. 将相同节点部署到用户测试机，保留地址与拓扑配置，补齐物理跨机器证据。
7. 将可运行的框架接入健身房长程剧本，持续评估连贯性、承诺、改口和跨日任务。

## 8 与历史路线的关系

识雨 A 方案采用单一 DSH 插件核心，任务、记忆与设备执行围绕该核心组织。DS-Group 当前方向采用共享聊天服务和多个独立 Bot 节点，中心与个体分别维护所属状态。

现有任务核验、产物、事件身份、回执和健身房可以按功能接入。每次复用都指定状态的主要保存方，避免同一任务、记忆或消息被多个调度器同时当作独立工作处理。识雨旧模块未完成工作继续按 DSH 接手边界推进，DS-Group 的新框架按本轮 Codex 授权推进。
