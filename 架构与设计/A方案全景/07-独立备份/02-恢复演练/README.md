## 主方案与输入输出

使用 restic 官方 restore 到新的隔离根，调用 SQLite 完整性检查、manifest hash 校验与业务验收集。复用备份和恢复入口的同一条路径，避免专门为演示做一套“总能成功”的恢复脚本；不恢复到正在使用的数据根，也不连接真实外部发送或物理执行器。

本轮复用收敛：固定 restic 0.19.1 的 `restore <snapshotId> --target <fresh-root>` 与 `check --read-data`，Ombre `115d831` 的 `extract_backup_archive_file` / snapshot validators，任务模块同一份 Superagent 适配 reconcile。只新增识雨业务断言和计时报告；不新增解包器、备份引擎或演练专用重试器。可局部复用 Ombre `tests/test_backup_archive.py`、`test_backup_import_safety.py` 的案例，保留 MIT 声明；本轮未复制、未运行上游测试。详见[逐模块复用证据](<../../../../research/2026-11-01-复用核查/恢复备份.md>)。

V22 补充：Ombre 组件 ≤256 MiB，总组合仍 1 GiB；验证 512 MiB 上限拒绝、legacy 无 manifest 不标 verified，以及写入静默证据缺失时不能报跨组件一致。V23 补充：组件写入一半故障仍可明确核对；Superagent 保留 effect 行不能自动推出可重发。对跨组件未知，必须保留恢复屏障，不虚报只读就绪或 RTO 达标。

V22 / V23 同时验证必需 `dsh-goal-sessions`：仅备份 GoalBinding 绑定的目标专用 Session log 与必要 projection 定义/配置，水位来自实际 log seq / GoalRef revision，含原生 phase/armed 与兼容版本。缺失或截断日志、projection 版本不兼容、flush/静默证据不足必须拒绝 complete/read-ready。恢复前关闭目标调度出口，恢复目标先 disarmed，再核对 GoalRef/phase、本地 stop/取消和当前授权；旧 armed=true 不得自动重启目标，无关聊天不得被纳入夹具导出范围。

输入为指定 snapshot ID、Bundle manifest、固定软件与 schema 兼容清单、独立恢复凭据、最新删除 / 撤权 / 停用记录以及验收数据集。输出 DrillReport：drillId、snapshotId、captureTime、failureAt、startedAt、readyAt、恢复环境、检查项、失败证据、RPO / RTO、unresolvedEffects、是否允许激活。只用 `latest` 而不固定实际 snapshot ID 不能形成可复查报告。[restic 官方恢复说明](<https://restic.readthedocs.io/en/stable/050_restore.html>)。

## 场景与通过标准

| 场景 | 设计数据与故障注入 | 通过标准 |
|---|---|---|
| V22：正常一致副本 | 1 GiB 对象、1000 任务，备份期间持续追加与删除 | SQLite integrity / foreign-key 检查通过；manifest 对象 hash / size 100% 匹配；水位来自快照而非 live |
| V22：损坏与缺失 | 损坏一个对象、截断 manifest、不可读仓库 / 错误密码 | 明确失败，未激活新根；不从模型补写缺失材料 |
| V22：删除后恢复旧快照 | 从删除前 snapshot 恢复，并叠加较新墓碑；另做墓碑不可取得案例 | 被删数据不能进入索引、ReadView、导出；墓碑不明时保持恢复锁 |
| V21 / V23：任务未知 | 100 个 effect 在发出后、回执前故障；包含用户取消与暂停 | 无自动重发；可核对的恢复到实际结果，无法核对的仍 unknown；取消、撤权和暂停不丢失 |
| V23：版本与代际 | 新 schema、旧二进制、不兼容配置、迟到 worker | 不兼容组合拒绝启动；旧 fencingToken 不能提交；从副本回退不覆盖较新 live 数据 |
| V27：主盘 / 主机不可用 | 使用真正独立目的地及独立恢复凭据，原机资料不可依赖 | 恢复仍可完成；准确记录覆盖的是独立盘、独立主机还是异地范围，不夸大故障域 |

首轮 3 个连续成功周期才算基线通过；每次存快照 ID、版本、时间、对象计数、校验摘要和任务状态差异。纯本地测试仓库可验证逻辑，但不能替代 V27。

## RPO / RTO 与调度

- **RPO**：故障发生时刻减去最后一份已完整备份且通过验证的 bundle captureTime；没有可验证副本时为未知 / 不达标，不以最近“开始备份”替代。默认目标 ≤15 分钟。
- **RTO**：从宣布启动恢复到新根达到只读业务校验通过、删除与任务核对完成的时长。合成 1 GiB 默认目标 ≤30 分钟，另报下载、校验、迁移、重建与人工等待分段时间。
- 目标不包括替换硬件到货时间；真实设备的不可查询副作用可以仍 unknown，但这些动作的派工保持阻断。只有开放动作后的检查也通过，才可报告“业务执行已恢复”。
- 每周做一次隔离恢复演练；schema / 备份工具 / 凭据策略变更后追加一次；生产目的地与数据量变化时重新测量目标。演练触发安排是未来运行设计，本轮不创建定时任务。

## 失败处置、数据生命周期与替代

演练失败使“最近恢复验证”状态变红并阻止相关升级或清理最后良好副本；它不直接停掉仍正常工作的生产核心。排查顺序为凭据与可达性、仓库完整性、bundle、版本兼容、业务核对；修正后必须再次从仓库恢复，而非只重跑已解压副本的局部检查。

演练数据只留在未来 `测试/YYYY-MM-DD-识雨主动运行/` 的专用根，用合成资料；实验结束停止所有恢复实例，删除可重建大文件前先保存报告、hash 与必要失败证据。真实恢复另按已经明确的范围执行，密钥不入报告。隔离恢复不得继承旧设备令牌后自动连真实客户端。

大数据量导致 30 分钟目标失效时，先分离关键状态与可重建索引、测量恢复路径；若 RPO 要求显著低于批量检查点能力，再评估成熟日志复制 / 备份产品，保留单一写入者与恢复屏障，不默认自研多主容灾。
