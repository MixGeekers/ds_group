## 1. 核心判断

目前没有证据要求识雨立刻脱离 DSH。DSH 的插件可以接入模型、会话、事件、工具、持久化和界面；插件也能组织后台任务。当前需要补齐的是识雨自己的运行体系：持续目标、可查询的自身状态、任务与授权记录、恢复流程、设备能力与数据生命周期。

建议在设计上让识雨的身份、内部状态、任务及协议具有自己的定义，由 DSH 提供当前宿主能力。即使起步时都运行在一个插件包 / 一个宿主进程中，也不要把识雨的全部状态绑定到某一条聊天 Session。这样可以保留后续拆出独立核心的选择，而不预先承担分布式系统的成本。

这里增加的是运行基础设施与设备执行面。用户已有的**内层六部分、外层对话与队列、外层对内只读、内外双工**保持不变。设备接入先作为“能力”的执行基础设施讨论，不悄悄把外层“只负责对话”改成外层可以任意行动。

## 2. 将“主动”拆成可实现的闭环

主动性的候选来源包括：用户给出的持续目标、明确承诺及截止时间、允许订阅的外部事件、运行健康变化、周期性回顾和经过验证的能力改进机会。

~~~text
事件 / 时间 / 目标差距
        ↓
去重、判断新鲜度、检查持续目标与授权范围
        ↓
core：结合内部状态判断是否值得做、何时做、预算多少
        ↓
形成带范围和完成条件的任务 → 委派 worker
        ↓
核验结果 → 更新任务；需要时由内部提交状态变更
        ↓
replyer 取得只读视图，在合适时机表达
        ↓
观察实际效果，决定后续跟进、结束或调整
~~~

识雨可以主动组织内部回顾和行动；replyer 仍然只负责获准的表达。人格、关系和情绪可以作为内部判断的依据，不能直接替代行动授权、客观事实或任务完成证据。它们怎样影响优先级仍需专题设计。

建议采用“事件驱动 + 必要的周期检查”。简单存活、空间和连接检查由程序完成；需要语义判断时才调用模型。每个持续目标记录适用范围、优先级、截止 / 复查条件、预算、暂停状态与完成条件，减少无事可做时反复调用模型。

既有 DSH-Superagent 可参考 Mandate / Ticket / Assignment、后续消息归属和 durable effects；DS-Bot 可参考侧边回复、长会话与技能提案。两者的机制不自动决定识雨的任务权限或模型数量。

## 3. “预留空间”需要定义哪些内容

先将用户想法理解为**可定位、可盘点、可迁移的识雨运行与数据空间**。固定目录、专用卷 / 配额、容器和虚拟机是不同选择；本轮不擅自决定物理磁盘、大小或隔离方式。

以下是未来逻辑区域建议，不是在当前资料工作区创建这些目录：

| 逻辑区域 | 内容 | 写入与恢复要求 |
|---|---|---|
| 内部权威状态 | 六部分内层的正式数据、身份与版本；具体表示未定 | 由内部受控提交；保留来源和一致性，不能依靠缓存或聊天摘要恢复 |
| 目标与任务 | 持续目标、授权、任务状态、执行记录、待发送回执 | 重启后可判断未开始、进行中、完成、失败或结果未知 |
| 原始经历与证据 | 按保留政策接受的事件、正文引用、操作证据 | 与长期记忆区分；记录来源、期限及删除传播范围 |
| 工作与产物 | 每个任务的工作目录、下载、中间材料与最终结果 | 按任务计量，明确哪些可清理、哪些要保留 |
| 可重建数据 | 检索索引、派生摘要缓存、临时文件 | 有明确原始来源；损坏可重建，不能反向成为事实来源 |
| 运行与配置 | 插件版本、依赖清单、设备登记、策略与诊断 | 稳定版与候选版分开；凭据通过专门设施引用，不放进普通模型上下文 |
| 恢复材料 | 本地检查点、恢复清单、校验与恢复记录 | 本地快照帮助快速回退；抵御整盘故障仍需独立故障域的备份 |

**逻辑归属、实际落盘位置、访问权限、外发范围是四张不同的清单。** 预留空间也不自动形成硬配额；若需要容量保证，应由文件系统 / 宿主资源控制实际执行。磁盘不足时可先回收已声明可重建且不被使用的缓存，延迟新任务；不能把删除权威记忆当作默认释放空间办法。

DSH 有 Harness home 与 profile；但切换工作目录不会改变全部权限、已启动进程或原项目身份，Electron 的部分数据也不由 DSH_HOME 重定位。因此仅指定一个 cwd 不足以实现“所有内容都在预留空间中”。建议未来为识雨选择独立的宿主数据范围，并登记必要的宿主外置项；是否使用单独 DSH_HOME 尚未决定。[工作目录语义](<https://github.com/deepseek-ai/deepseek-harness/blob/ce7073d51254c26cd63b22a60835b8f948deb447/docs/subsystems/working-directory.md#L5-L15>)、[桌面设置位置](<https://github.com/deepseek-ai/deepseek-harness/blob/ce7073d51254c26cd63b22a60835b8f948deb447/apps/desktop/README.md#L289-L293>)

此外，本地落盘范围不说明网络流向。所查上游基础配置挂载 DeepSeek 会话日志贡献组件，其文档默认 enabled=true；模型请求、额外会话日志贡献、反馈遥测、备份与设备传输需分别决定。没有检查本机 profile，不能声称当前安装正在上传；也不能仅以本地保存就承诺数据不外发。[配置与说明](<https://github.com/deepseek-ai/deepseek-harness/blob/ce7073d51254c26cd63b22a60835b8f948deb447/apps/cli/reference/README.md#L135-L141>)

## 4. 让识雨知道自己的实际状态

建议为内部提供一个有时间和来源的“运行状态视图”，包括：

- 自身实例身份、软件 / 数据版本、当前宿主与启动时间。
- 预留空间的路径映射、容量、占用、可重建项与保留策略。
- 当前有效能力、设备标识、连接状态、授权范围及最近成功探测时间。
- 正在进行 / 等待 / 结果未知的任务，以及资源预算和暂停状态。
- 最近一次备份、校验与恢复演练的结果；没有验证就显示未知。
- 模型与网络依赖是否可用，以及可执行的降级动作。

这张视图应由实际服务探测和权威记录生成，模型按需读取。自述“我能控制某设备”须与当前能力状态对应；配置过某工具并不代表当前能用，心跳正常也不代表应用功能正常。视图不能包含密钥明文，模型不能通过改写描述文件就把失效能力变成可用。

建议将“声明支持”“当前可用”“最近验证过”分开表示。replyer 使用裁剪后的只读视图解释状态；环境探测结果与长期记忆仍是不同数据。

## 5. 自愈：按故障发生的位置分工

| 故障层级 | 建议恢复方式 | 限制与完成凭据 |
|---|---|---|
| 单次模型 / 工具请求 | 有上限的退避重试，必要时使用已配置替代路径 | 非幂等外部动作先查结果；超时不能直接解释成未执行 |
| 某个任务或设备连接 | 重建执行实例、重连、核对任务状态、继续未完成步骤 | 新实例保留原任务身份和授权；旧实例的迟到结果不能覆盖新状态 |
| 索引 / 缓存损坏 | 核对权威原文，重建并用已知查询验证 | 原文也损坏时必须转备份恢复，不能用模型补写事实 |
| 插件配置 / 升级失败 | 进入已知可用配置，保留故障证据，回退兼容版本 | 二进制回滚与数据迁移分开；不能直接覆盖升级后新产生的记忆 |
| DSH / 识雨主进程退出 | 进程外的监督机制按期望运行状态重启、切换或进入恢复模式 | 已停止的进程无法执行自己的恢复代码；明确的用户停用不能被当成故障反复拉起 |
| 主机掉电、磁盘故障或基础网络故障 | 独立备份、其他授权主机或人工介入 | 同机守护进程解决不了整机故障；是否要求异机接替尚未决定 |

DSH 已有部分错误诊断、插件生命周期及原生配置恢复路径；静态看到的 sanitizeProfile 会备份 profile patch、恢复指定 bundle 列表，并要求调用方已停止 profile、排除并发写入。它不是识雨全面自主恢复已经完成的证据。[实现](<https://github.com/deepseek-ai/deepseek-harness/blob/ce7073d51254c26cd63b22a60835b8f948deb447/packages/boot/app-boot/src/profile-sanitize.ts>)

建议把恢复循环定义为“发现 → 分类 → 执行已知修复 → 校验 → 恢复任务 / 降级”。反复失败有次数、时间与资源上限；应留下能解释当前状况的记录。进程外监督器尽量简单，不依赖正在故障的模型或同一份可被插件改坏的配置。

自愈与自我改进也要分开：重新连接或重建缓存是恢复既定能力；改源码、改策略、改人格或引入新技能属于变更。后者可以研究“提出变更 → 隔离验证 → 小范围启用 → 观察 → 回退”的流程，不把即时修改运行中的自身代码当成全部自愈。

## 6. 多设备：统一能力和任务身份，保留设备差异

建议先采用一个维护权威内部状态的中心，多个设备端承担感知和执行。设备端可以是专用客户端、已有代理或适配器，不必每台都部署一个完整人格与模型。

~~~mermaid
flowchart LR
  channel["对话渠道"] <--> outer["外层：replyer 与对话队列"]
  outer -->|"观察事件、只读查询"| core["内层：core 组织六部分状态与主动判断"]
  core -->|"授权视图、通知、回执"| outer
  core -->|"带范围的任务"| worker["worker：执行并返回证据，层级待定"]
  worker --> gateway["设备能力与任务路由"]
  gateway <--> clients["Mac / Windows / Linux / 其他设备客户端"]
  worker -->|"结果或变更提案"| core
  core <--> state["预留空间：权威状态、任务与恢复材料"]
~~~

这是逻辑方案，不是已经确认的进程部署图。设备接入仍属于能力基础设施；外层不因此获得内部写权限。需要真正强隔离时，工具范围、文件权限与执行沙箱也须落实，不能仅靠插件命名或隐藏一个工具按钮。

设备协议建议至少涵盖：稳定设备 ID、配对与撤销、能力版本、健康状态、每任务范围、任务 / 请求 ID、执行状态回报、文件引用和取消。远程路径必须带设备身份，不能把两台设备的同名路径当成同一文件。

连接情况应影响任务处理：

- 尚未开始的任务：根据期限和目标可等待、改派或取消；改派前释放原执行资格。
- 已经开始但掉线：标记结果未知，恢复连接后核对，不能默认重放点击、发送、付款或文件变更。
- 离线期间：设备端只按既有授权与有效期执行允许离线继续的任务，保存回执；是否继续由任务类型决定。
- 同一桌面或物理设备：通常需要独占控制及可见的忙闲状态，不能让两个 worker 同时争用鼠标或执行冲突动作。
- 机器人：高频控制、故障停止与急停留在设备本地；语言模型负责较高层的任务，不依赖远程对话链路维持即时控制。

现有 [多机控制候选](<../技术候选/多机控制.md>) 提供网络、远程管理、GUI 与 ROS 的参考。DSH 上游也已有 MCP 客户端和 POSIX SSH provider，可减少起步接入工作；MCP 本身不包办设备配对、系统权限、离线队列或 GUI 操作。SSH provider 的核查范围是 POSIX，不能外推为完整 Windows / 移动设备 / 机器人支持。[MCP](<https://github.com/deepseek-ai/deepseek-harness/blob/ce7073d51254c26cd63b22a60835b8f948deb447/packages/mcp/mcp-client/README.md#L26-L67>)、[SSH](<https://github.com/deepseek-ai/deepseek-harness/blob/ce7073d51254c26cd63b22a60835b8f948deb447/packages/ssh/README.md>)

## 7. 两种运行形态的比较

用户先要求比较，随后选择 A 作为当前架构基线。以下保留比较依据，B 为未来备选；两种形态都保留 DSH 插件入口。

| 比较项 | A：识雨核心运行在 DSH 插件中 | B：独立识雨核心 + DSH 插件适配 |
|---|---|---|
| 权威状态与任务由谁维护 | 插件内的识雨服务；持久数据独立定义 | 独立核心服务；DSH 只通过协议读取、提交结果和接收任务 |
| DSH 的角色 | 模型、会话、工具和识雨的直接宿主 | 对话入口与可替换的执行宿主之一 |
| 界面关闭 | 宿主仍运行时可以继续；可使用持续运行的 Web 服务 | 核心不依赖界面，执行仍取决于各执行器是否在线 |
| DSH 主进程退出 | 识雨的判断和调度暂停；外部监督器可拉起后恢复 | 核心可以继续收事件、排队与设备管理；DSH 专属执行仍暂停。若要求继续模型推理，须另有独立模型 / 执行路径 |
| 自愈边界 | 宿主内恢复 + 宿主外启动 / 回退机制 | 核心可管理 DSH 的恢复；核心本身仍需要进程外监督 |
| 权限边界 | 同进程的受信插件逻辑隔离；严格执行隔离还需额外机制 | 服务边界更清楚，但客户端认证、接口授权与更新兼容要自己维护 |
| 多设备连接 | 插件可管理设备协议，或调用既有设备中枢 | 核心统一管理设备，DSH 是其中一个工作入口 |
| 开发与维护成本 | 可以复用更多 DSH 机制，起步工作较少；受宿主生命周期与 API 变更影响 | 要维护通信、状态查询、恢复、协议版本与部署；故障范围更易分开 |
| 数据一致性 | 以一个识雨写入者为起点 | 仍建议单一权威写入者；独立服务不自动要求多主复制 |
| 适合的要求 | 允许依赖 DSH 服务持续运行，优先验证主动闭环 | 明确要求跨宿主存续、DSH 更新期间继续管理任务，或必须有更强进程边界 |

**当前决定：**用户已选择 A。继续建议在数据格式和任务协议上保留未来拆出核心的可能性；这不是现在实现 B 的要求。A 可以研究专用 DSH 服务和外部进程监督，具体进程管理方式未定。若将来升级 B，应由明确的独立存续或故障隔离要求推动。

DSH 文档中的 headless 是一次性 runner，不应直接当成常驻守护服务；Web 与 SDK 是不同应用形态，具体持续运行与重启策略仍要选定。[宿主形态](<https://github.com/deepseek-ai/deepseek-harness/blob/ce7073d51254c26cd63b22a60835b8f948deb447/docs/architecture.md#L13-L45>) 关闭桌面主窗口与退出宿主进程也不同；当前已安装版的实际行为待验证。[桌面行为说明](<https://github.com/deepseek-ai/deepseek-harness/blob/ce7073d51254c26cd63b22a60835b8f948deb447/apps/desktop/README.md#L70-L80>)

## 8. 与已有资料的分工及取舍

| 已有资料 | 本轮继续参考的部分 | 尚需识雨自己的设计 |

| [DSH-Superagent](<../技术候选/DSH-Superagent.md>) | 授权 / 工单 / 执行实例、任务归属、状态提交与回执 | 适配非编码任务、内层六部分、只读 replyer |
| [DS-Bot](<../技术候选/DS-Bot.md>) | 长期对话、快照式侧边回复、上下文续接、技能提案 | 记忆提交权、视图范围、能力改进验证 |
| [记忆决策调研](<记忆决策模型调研.md>) | 规则边界、模型提案、程序核查、受控提交 | 六部分内层相互影响的具体表示与评测 |
| [多机控制](<../技术候选/多机控制.md>) | 可达网络、远程管理、GUI 和机器人执行器候选 | 统一设备身份、能力、授权与任务结果协议 |
| [备份](<../技术候选/备份与检查点工具.md>)与[机密存储](<../技术候选/机密存储工具.md>) | 备份校验、恢复、密钥与数据分离 | 活跃数据一致性、恢复验证、保留 / 清除政策；不能沿用早期小文档场景代替运行系统设计 |

本轮不追加整套数据库、消息中间件或多个设备管理平台。先定义它们要满足的契约，再决定是否需要独立产品。

## 9. 最小验证计划与未决问题

以下仅为计划；后续明确要求实验时进入 `测试/YYYY-MM-DD-识雨主动运行/`，采用合成数据、替身设备与固定宿主版本。

| 假设 | 同一场景比较办法 | 通过条件 |
|---|---|---|
| 主动性不依赖对话窗口 | 关闭界面，触发同一外部事件与到期目标 | 任务产生、执行与回执符合目标；不把收到提醒当作已完成 |
| 空间可盘点且受控 | 列举所有写入路径和外发路径，制造缓存增长 | 权威 / 临时 / 外置项可说明；配额与保留策略有效，无误删正式数据 |
| 故障可恢复 | 在受理、执行、外部完成、记回执之间注入退出 | 恢复后无丢任务、无盲目重放；未知状态明确；用户暂停保持有效 |
| 自愈有实际效果 | 破坏可重建索引或可回退配置，复验已知查询 / 功能 | 修复后功能恢复，权威数据未被猜测补写；失败达到上限后停止循环 |
| 多设备执行一致 | 设备掉线、重复消息、迟到结果、设备改派 | 不重复执行或被旧结果覆盖；设备端与中心能核对任务状态 |
| A 的暂停和恢复边界真实 | 停掉 DSH，验证外部监督与重新启动后的状态核对 | 退出期间不虚报核心仍在运行；恢复后区分任务和设备结果，统计恢复时间 |
| 主动工作值得做 | 在固定目标下记录有效成果、无效动作和打扰 | 有效成果、响应延迟、资源费用和误触发都能测量，不以调用次数代表能力 |

仍需决定：空间的物理形式与容量；首次连接哪些设备及能力；持续目标与自动行动范围；可接受的停机 / 数据损失；备份故障域；A 的宿主进程管理方式。数据库与模型组合继续待定；若未来出现必须脱离 DSH 存续的要求，再重新评估 B。
