# 记忆决策模型调研

- **调研日期：2026-10-30（America/Caracas）。**
- **状态：资料与限定源码核查完成；适配建议待讨论，未实施。**
- **范围：**围绕“是否保存、如何更新或遗忘、何时读取和整理上下文”的决策，不是对所有通用推理模型的排行榜比较。
- **方法：**核对作者论文、官方代码与文档；冻结关键仓库提交和论文版本。没有运行训练、基准或候选系统，也未独立复现作者成绩。

## 1. 先给结论

**当前已有足够的工程与研究基础，让一个受约束的内部模块判断哪些信息值得保存；但本次证据不支持把长期记忆、删除、人格与能力变化都交给一个不受检查的“万能决策模型”。**

三个层次必须分开：

1. **机制是否能实现：**结构化抽取、记忆文件编辑、版本管理、任务反馈重排等，已有公开工程实现。
2. **策略是否可以学出来：**受控任务中的记忆操作与上下文管理已有 RL 研究；不同方法的代码可获得性和复现程度差异很大。
3. **是否值得信任：**答题或任务成绩提高，不等于误写、错归属、错误删除、隐私与长期稳定性已经解决。

对识雨的初步建议是：**先让 core 控制一条“规则边界 + 模型提案 + 程序校验 + 可追溯提交”的内部决策链，不急于先训练专用决策模型。** 这是一项建议，不是已经选择技术栈或批准自动写入。

## 2. “决策模型”实际包含不同问题

| 问题 | 可以怎样处理 | 不能混淆的边界 |
|---|---|---|
| 是否允许保存 | 用户指引、数据范围、权限和保留政策 | 不能仅因模型认为有用，就越过保存许可 |
| 内容是什么、是否值得留 | 通用 LLM、专门分类器或训练策略，结合来源与历史 | 语义判断和自报置信度不等于事实验证 |
| 是否重复、冲突或过时 | 检索、时间与归属对照、版本关系 | 相似不等于同一事实，最新提及也不总是最可靠证据 |
| 如何处置记忆 | 新增、保留、提出修订、延迟、明确清除等动作 | 论文中的 Delete 不等于生产数据所有副本已清除 |
| 哪条记忆有助于当前任务 | 相关性检索、重排、基于反馈的效用学习 | 学会“拿哪条”不等于学会“该不该存” |
| 谁能提交变更 | core 控制的权限与一致性机制 | 模型输出了动作，不代表输出者获得执行权 |

## 3. 发展阶段：多条路线并存，而非单线升级

以下成熟度是本次适配评估，不是统一的行业评级。

| 路线 / 代表 | 真正改变的对象 | 本次核得的阶段 | 对识雨的判断 |
|---|---|---|---|
| 规则 + 程序校验 | 可执行边界、字段、来源、版本和保留规则 | 常规工程基础；语义覆盖有限 | 应作为权限与提交的基础，不承担全部内容理解 |
| [Mem0](<../技术候选/Mem0.md>) | 通用 LLM 抽取的外部记忆记录 | 当前公开主路径是单次 ADD-only，代码完整；不是专门 RL 写入策略 | 可借鉴结构化候选与追加式记录，不照搬默认保存范围 |
| [Letta](<../技术候选/Letta.md>) | 记忆文件、上下文和 skills | 当前 MemFS / reflection 工程可查，使用通用模型与维护提示 | 可借鉴耐久知识筛选、回顾与版本化；写权限要收回内部 |
| [Memory-R1](<../技术候选/Memory-R1.md>) | Memory Manager 与 Answer Agent 的模型策略 | 论文报告学习 CRUD / 筛选有效；作者仓库仍待发布实现 | 作为研究参考，不按现成组件选型 |
| [AgeMem](<../技术候选/AgeMem.md>) | 统一长期记忆和短期上下文工具调用策略 | 有真实 RL 训练与评估代码，但仍是研究实现 | 若后续需要训练专门策略，值得跟踪；先做影子评估 |
| [MemRL](<../技术候选/MemRL.md>) | 每条经验的效用 Q 值及检索排序 | 冻结 LLM，运行时更新记忆元数据；有研究代码 | 更适合有可验证结果的 worker 经验检索，不替代保存许可或完整生命周期决策 |

### 时间线中的两个重要变化

- **2025—2026 的研究推进：**Memory-R1 将记忆操作与筛选作为可训练策略；AgeMem 进一步统一长期存储和当前上下文操作；MemRL 走不更新 LLM 权重的运行时效用学习路线。三者优化对象不同，不能都简称为同一种“自我学习”。
- **工程产品并不总是增加自动改写：**本次 Mem0 快照已从旧四操作默认流程转向 ADD-only；Letta 现行代码迁移并采用文件化 MemFS。因此，不能把旧教程中的实现直接当作“目前的方案”。

## 4. 关键证据与限制

### 4.1 Mem0：从四操作介绍到追加式默认路径

2026-10-26 快照的实际默认流程为最近消息与相关已有记忆 → 单次 LLM JSON 抽取 → 哈希去重 → 新增；显式 update / delete API 仍存在。空抽取时也会保存输入消息，不能把空 `memory` 当作所有数据都没有保存。

这说明减少自动覆盖可以是一种工程取舍：保留历史，但冲突、时效和权威版本仍需处理。旧四操作提示词虽还在源码中，已不能代表当前默认执行路径。

来源：[迁移说明](<https://github.com/mem0ai/mem0/blob/26cdefb46600c0fa5953c4b5ee5003c125539fc4/docs/migration/oss-v2-to-v3.mdx#L14-L40>)、[当前执行链](<https://github.com/mem0ai/mem0/blob/26cdefb46600c0fa5953c4b5ee5003c125539fc4/mem0/memory/main.py#L918-L1041>)。

### 4.2 Letta：把记忆编辑当作待验证假设

当前 MemFS 以 Git 管理文件记忆，reflection 根据纠错、耐久偏好和流程整理上下文；维护规则要求模式或明确指令，而非单次含糊事件，并将一次编辑视作需要后续检验的假设。

这是可用的工程思想，不是已证明可靠的自主心理变化机制。其默认记忆编辑权不能原样赋给识雨外层；Git 可审计也不等于从全部历史中彻底删除。

来源：[MemFS](<https://docs.letta.com/concepts/memfs/index.md>)、[维护规则](<https://github.com/letta-ai/letta-code/blob/89a757f93cf2a84c74bc16a27b63b6c61f95892c/src/skills/builtin/maintaining-core-memory/SKILL.md#L56-L121>)。官方明确其学习发生于上下文管理，而非模型权重更新：[官方概览](<https://docs.letta.com/llms.txt>)。

### 4.3 学习型策略：任务效果有证据，长期治理尚不能外推

- **Memory-R1：**论文训练 Memory Manager 选择 ADD / UPDATE / DELETE / NOOP，并训练回答阶段筛选记忆；作者实验用 152 个 LoCoMo 训练 QA，但这不等于只有 152 次总交互或训练成本很低。作者仓库仍为 Code coming soon。[v5 论文](<https://arxiv.org/abs/2508.19828v5>)、[代码状态](<https://github.com/yansikuan/memory-r1/blob/9c413a2413c4fee160ec05445856c1529d63ac7a/README.md#L14-L30>)。
- **AgeMem：**六种工具覆盖增改删、检索、摘要和过滤，有实际训练代码；默认存储为内存实现，持久化需另做，论文与当前代码的奖励配方也需核对。它证明了可研究的策略路线，不是开箱即用的个人长期记忆服务。[v3 论文](<https://arxiv.org/abs/2601.01885v3>)、[存储实现](<https://github.com/y1y5/AgeMem/blob/98f563f907d67b2f2436e3ae7b7ceff32e482814/trinity/common/workflows/memory_context/memory_store.py#L31-L40>)。
- **MemRL：**冻结 LLM，用结果反馈更新记忆 Q 值；这是可变的检索效用状态，不是通用存储政策。多轮累计成功率与重复暴露的记忆化，不能转述成一次性未见任务能力；作者特别说明 HLE 部分的重复暴露边界。[v2 论文](<https://arxiv.org/abs/2601.03192v2>)、[实际 Q 更新](<https://github.com/MemTensor/MemRL/blob/c1b322ca43de36ddf64c6712f89d0095bfc35ce0/memrl/service/value_driven.py#L181-L219>)。

本次没有核实这三项完整、同设置的独立复现成功。这里说的是核查范围，不是断言外界不存在任何复现。

## 5. 识雨第一版的决策链候选

结合用户的 core / worker / replyer 与只读双工约束，建议把决策留在内部：

```text
外层 / replyer：传递观察事件，只读获取上下文
                   ↕ 双工消息，不是内部写接口
core：保存范围与权限检查
  ↓
内部委派的 worker：提取候选、对照历史、列出依据与不确定性
  ↓
core：模型建议 + 程序校验 + 风险 / 版本检查
  ↓
提交 / 拒绝 / 延迟 / 需要时向用户澄清
  ↓
向外层发送真实结果回执或更新后的只读视图
```

worker 归属和权限仍是待定设计；图中是建议让 core 委派内部分析，而不是让外层主动选择记忆动作。core 也不必等于一个包办所有事情的 LLM：它可以包含状态机、规则和受限模型调用。

### 决策时先问六类问题

1. **许可与范围：**是否允许长期保存？是否包含不应留下的秘密、敏感内容或其他人的未经确认资料？禁止项不能被“未来有用”打分覆盖。
2. **来源与归属：**谁在什么时候说了什么？是用户陈述、引述、角色扮演、观察结果，还是模型自己生成的内容？
3. **未来用途与时间尺度：**耐久偏好、明确承诺、重要决定、可复用经验可能值得保留；一时情绪或临时任务状态不能直接晋升为稳定人格结论。
4. **新颖性与冲突：**已存在、补充细节、明确纠正、阶段性变化还是尚不能解释的矛盾？不因语义相似就合并不同事件。
5. **证据与不确定性：**可核对依据在哪里？不确定时可以延迟或澄清，而不是自动补全。模型自报置信度只能作参考，不能直接当校准过的概率。
6. **影响范围：**新增一条带来源的经历，与修改人格、能力、关系结论或彻底删除资料，风险不同，不宜共用一个自动提交门槛。

### 建议动作接口

初期可以使用 `NOOP / PROPOSE_ADD / PROPOSE_SUPERSEDE / DEFER / NEED_CLARIFICATION` 等明确动作，名称尚未定稿。合并、降级、撤回及真正删除可作为受控的独立动作，不要求一开始全部自动化。

- `NOOP`：判断无需新增；不能混同于模型调用或解析失败。
- `DEFER`：材料不够，暂不作权威更新；暂存候选也需遵守保留政策。
- 提案应带事件身份、来源位置、归属者、事件时间、目标 / 基础版本、建议动作、理由与不确定性。
- core 校验 schema、目标是否存在、来源是否属于该事件、权限范围、版本冲突与重复处理，再决定提交。
- **用户明确要求彻底删除时，不能用软删除或可回滚历史冒充完成。** 可撤回的普通修订与隐私清除应分开；清除须覆盖约定范围内的原文、派生索引、历史与备份。
- **检索分数也是状态。** 若采用 MemRL 式反馈，Q 值更新仍要走内部权限和审计，不能交给 replyer 直接操作。

## 6. 怎样判断它真的会决策

先构建适合识雨语言与场景的小型人工标注集，并保留从未用于调提示词的测试集；固定基础模型、预算与抽取 / 检索条件，不只比较最终聊天是否流畅。

| 样例类型 | 应验证什么 |
|---|---|
| 明确耐久偏好、约定或决定 | 值得保存的内容不被漏掉，来源与时间正确 |
| 寒暄、重复陈述、临时状态 | 不无意义膨胀，也不把暂时状态当稳定特征 |
| “我以前说错了”、偏好随时间变化 | 区分纠正与历史变化，不误删有价值的时序证据 |
| 引用他人、角色扮演、反话、模型自述 | 不错误归属，不把生成内容当已证实事实 |
| “不要保存这段”“请彻底忘掉” | 保存与删除政策真正生效，包含副本与日志边界 |
| 并发、重复投递、过时结果 | 无重复记忆、无旧版本覆盖，回执可核查 |
| 记忆中的越权指令 | 历史数据不会变成当前写权限或上级指令 |
| 能力改进与任务经验 | 记住经验后，在保留任务上是否更少犯同样的错 |

建议分别看：误写率、漏写率、错归属、错误合并 / 覆盖 / 删除、来源可追溯性、澄清比例、成本与延迟；再看检索与下游任务效果。不能用单一 QA 总分替代所有指标。

### 外部评测能借什么，不能替代什么

- **LoCoMo（ACL 2024）：**公开发布含十组长对话，主要支持问答、事件总结等研究；不是长期私人生活的完整覆盖。[官方数据说明](<https://github.com/snap-research/locomo/blob/main/README.MD>)。
- **LongMemEval（ICLR 2025）：**覆盖信息提取、多会话推理、知识更新、时间推理和不知道时的拒答。[作者仓库](<https://github.com/xiaowu0162/LongMemEval>)。
- **LongMemEval-V2（2026）：**进一步面向 agent 历史轨迹、动态状态、工作流程、环境陷阱与前提判断，并同时衡量答案效果与查询延迟；说明评测正在从“记住一句话”走向“能利用经验”。[作者仓库](<https://github.com/xiaowu0162/LongMemEval-V2>)。
- 各论文的样本、基础模型、裁判、检索预算、重复暴露与指标不同，不做跨表硬排名。Mem0 官方也明确某些成绩来自含专有优化的 managed platform，而非开源 SDK 或逐事实保存准确率。[官方评测口径](<https://github.com/mem0ai/mem0/blob/26cdefb46600c0fa5953c4b5ee5003c125539fc4/docs/core-concepts/memory-evaluation.mdx#L125-L140>)。

## 7. 建议推进顺序

1. **定义边界与样例。** 先明确内外权限、哪些值得记、哪些不能记，以及怎样判定保存 / 删除正确。
2. **做规则 + 通用模型的内部提案基线。** 先影子运行或只作用于明确授权的测试数据；不写真实权威状态，记录建议与人工答案差异。
3. **受控自动提交。** 只对已验证的低风险动作开放，保留来源、版本、失败说明和适用的回退机制；涉及隐私清除时采用真正清除路径。
4. **再判断是否值得学习策略。** 有稳定标注和反馈后，可考虑监督微调 / 蒸馏，或在奖励明确时研究 RL；可验证任务经验的检索效用可单独试验。

这条顺序不是永久限制自主性，而是先得到能够证明改进的反馈。没有目标、样本和可靠反馈时，训练一个更会执行记忆动作的模型，也可能只是更熟练地保存错误。
