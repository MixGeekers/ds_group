## 它是什么

既有探索以 Mac 上的 DSH 宿主为背景（见 [macOS完全控制](<macOS完全控制.md>)），不代表识雨已有正式设备控制运行系统。本候选回答“如何让授权的多台设备（含机器人）变成识雨的身体”。早期比较曾采用“组网可达 → 特权常驻代理 → 指令下发 → 各 OS GUI → ROS”路线。当前设计已改为现有网络/SSH/MCP + 现成局部执行器，特权常驻代理并非接入前提。以下早期“首选”表保留为历史备选，不代表本轮优先级。

## 可借鉴之处 → 识雨的最小路线

- **路线 A（推荐骨架）**:Headscale 组网 + MeshCentral 中枢（仅 VPN 可达）→ 每台授权设备装 agent（服务级权限）→ 识雨经 REST/`meshctrl`/SSH 下发，GUI 手按 OS 分配；机器人同骨架接入 + rosbridge 控制面。
- **路线 B（零新服务）**:SSH 密钥 + paramiko/pyinfra 自建薄层 + tmux；没有可被攻陷的中枢，代价是全靠自己写。
- **路线 C（快速体验）**:先自托管试用 cua，验证"远程机器当身体"的手感再建骨架。

## 限制与取舍

- **法律边界**:仅限自有/书面授权设备；未授权控制他人计算机违法。
- **中枢即最高价值目标**（MeshCentral/Headscale/Salt 管理面失守=全部身体失守）：仅 VPN 可达、双因素、及时升级。
- MeshCentral/TacticalRMM/NetBird/Fleet 许可证为 NOASSERTION 或非标准者，采用前逐个核对条款。
- 多层重叠（L3 与 Salt 的常驻 agent、L5 与 cua 的桌面流）——按设备规模做减法，不贪全。
- **2026-10-31 核查补充：**[DSH 上游](<DSH.md>)已有 stdio / Streamable HTTP MCP 客户端与 POSIX SSH provider 的文档和实现证据；本机版本的实际挂载、服务连通性与设备权限仍未验证。MCP、SSH 和 GUI 执行器承担不同职责，不能据此宣称已有统一设备客户端。
