# 渠道连接：OpenClaw 侧车与官方 SDK

日期：2026-11-01（America/Caracas）。范围：WhatsApp、QQ、飞书、对话队列与 DSH 边界。状态：**一手文档与限定源码静态核查；未安装、登录账号、运行候选或复制产品代码。** 使用识雨技术探索流程；不把渠道接入升级为迁移核心。对话与任务调度分工见[Core 派工与对话时序](<../../架构与设计/A方案全景/Core派工与对话时序.md>)。

## 结论与两条验证路线

**可以复用 OpenClaw 的对外连接能力，DSH 仍是识雨核心；但没有核查到可直接配置启用的现成 DSH bridge。** OpenClaw 渠道插件依赖它注入的 PluginRuntime、账号/配对、路由、入站与发送服务，不是把插件目录拷进 DSH 就能工作的独立传输库。

| 路线 | 已有可直接用的部分 | 必须补齐 | 本轮判断 |
|---|---|---|---|
| **统一渠道侧车**：OpenClaw + 原渠道插件 + 小型识雨接管插件 | 账号、WhatsApp QR/连接保活、平台解析/格式/媒体、目录、渠道配置、持久投递组件 | 认证桥、先持久接纳再接管、覆盖所有入口的失败阻断、发送授权和回执关联；少量但关键的宿主 guard 补丁 | 用户同时需要三渠道统一体验时优先验证；不因一个 hook 缺口排除其整合收益，尚不能称零修改直用 |
| **平台 SDK 直连**：SDK → ChannelAdapter → DSH | QQ 官方 SDK 已有完整 Bot 生命周期；飞书官方 SDK 已有高层 Channel，均包含重连/消息能力 | EventEnvelope、身份命名空间、业务持久接纳、取消/Effect 回执；SDK 内重试和降级需纳入授权检查 | 与侧车并行做最小对照；不是从 HTTP/WS 原语自建三个连接器。单 QQ/飞书需求闭包更小；WhatsApp linked-device 仍优先比较已有侧车 |

身份约定：connectionId 是持久连接，connectorAccountRef 是 OpenClaw accountId 或 SDK 服务账号引用，ParticipantAccount.accountId 是对方账号；不能把三者合并或按昵称匹配。

两路的核心、ConversationService、replyer 与 Effect 不变。先用一个合成渠道跑相同断线/重复/取消场景，再接真实测试账号。比较需要维护的补丁、丢失/重复/未知结果、账号生命周期、媒体与卡片覆盖、升级工作量；本轮没有耗时/性能实测，不能断言任一路整体工作量更少。若统一侧车只需边界明确的少量补丁且覆盖三渠道，优先保留；若必须修改多条推理/调度链才能阻止默认 Agent，采用官方 SDK 路线。

技术栈短标签：**DSH 核心｜OpenClaw 渠道侧车（条件验证）｜QQ Bot SDK / Lark Channel（并行对照）｜持久 inbox + p-queue + Effect outbox**。

## OpenClaw 纯渠道侧车：真实接缝与缺口

### 已核查的入口

- [ChannelPlugin 文档](https://github.com/openclaw/openclaw/blob/04fefb3455a0b0779909b251dbabb19f4d61db29/docs/plugins/sdk-channel-plugins.md)：插件负责平台事实、账号、发送、格式；core 负责 message 工具、路由/session、dispatch 等。
- [WhatsApp index.ts](https://github.com/openclaw/openclaw/blob/04fefb3455a0b0779909b251dbabb19f4d61db29/extensions/whatsapp/index.ts)用 defineBundledChannelEntry 和 runtime setter；[runtime.ts](https://github.com/openclaw/openclaw/blob/04fefb3455a0b0779909b251dbabb19f4d61db29/extensions/whatsapp/src/runtime.ts)缺少注入运行时会抛错。因此不推荐抽整个插件并伪造 PluginRuntime；保留完整侧车比复制庞大闭包更符合复用目的。
- [公开消息 hooks](https://github.com/openclaw/openclaw/blob/04fefb3455a0b0779909b251dbabb19f4d61db29/docs/plugins/hooks/messages.md)确有 `api.on("before_dispatch", handler)`，返回 `{handled:true}` 可无回复接管普通模型派发；`before_agent_reply` 是较晚的合成回复接缝，`message_received` 只观察，不能阻止默认 Agent。

### 不能省略的失败阻断

[hooks.ts](https://github.com/openclaw/openclaw/blob/04fefb3455a0b0779909b251dbabb19f4d61db29/src/plugins/hooks.ts)中 createHookRunner 默认 catchErrors=true；默认 fail-closed 的只有 before_agent_run、before_channel_ingress，before_dispatch 默认 fail-open。桥调用 DSH 失败后只抛异常，**不保证**停止 OpenClaw 普通推理。

[dispatch-from-config.choose-route.ts](https://github.com/openclaw/openclaw/blob/04fefb3455a0b0779909b251dbabb19f4d61db29/src/auto-reply/reply/dispatch-from-config.choose-route.ts)仅在 allowInboundHandlers 且不受 admittedSessionSettingsRestrictRuntime 限制时运行 before_dispatch；本次所见该 hook 载荷是文本/部分关联 ID，不能直接假定包含完整媒体事实。更早的 inbound_claim 有 typed media/providerUpdate，但[绑定分支](https://github.com/openclaw/openclaw/blob/04fefb3455a0b0779909b251dbabb19f4d61db29/src/auto-reply/reply/dispatch-from-config.prepare-operation.ts)在 missing_plugin/no_handler 时存在回退，不是天然永不回退的桥模式。

**有限补丁计划，而非已存在配置：**为明确列出的“识雨拥有的 channel/account”增加宿主层 dispatch guard：桥缺失、禁用、超时、拒绝、scope 不匹配、受限 session 或未覆盖的原生命令均停止/挂起该入站，不进入普通模型、工具或原生控制命令；将相关 claim 异常改为不放行。guard 在 bridge 插件之外持有，避免插件卸载同时移除保护；不影响未交给识雨的其他账号。Bridge ready 后才启动这些渠道消费者，升级时 fail closed。上述两个 dispatch 文件与 hooks 的边界是补丁候选位置，具体 hook/claim 放置需通过三渠道原生输入路径追踪后确定。

这比“设置 model=null”可靠，但**本轮未证明完整覆盖**；普通消息、媒体、群/@、编辑/删除、卡片、斜杠命令、重启/热重载均要验证。若覆盖补丁扩散或平台路径绕开 guard，改走 SDK 直连，不允许假装这是现成纯网关能力。

### 入站交接与崩溃窗口

平台事件 → OpenClaw 原生 durable ingress（有能力的渠道）→ 识雨桥 → DSH IngressService.accept → 持久 IntakeReceipt → hook 返回 handled。接纳键使用稳定 connectionId + providerUpdate.id，connectionId 绑定 provider/tenant/app/服务账号；只有 messageId 时合成 messageId+revision+eventKind，不用正文摘要代替消息身份。桥以稳定身份重投，DSH 回 duplicate 后同样结束接管。只有 DSH 已持久 accepted/duplicate 才确认跨进程交接；handled 本身不是 DSH 业务接纳证据。

DSH 接纳前桥崩溃：原生持久入站保留并重试；若具体渠道/SDK 没有这个能力，必须在确认传输消费前接入持久 journal 或明确 gap/补拉，不能声称不丢。DSH 接纳后、桥拿回执前崩溃：同键重送拿 duplicate。桥返回 handled 后 DSH 崩溃：从 DSH inbox 恢复。只有接纳回执丢失而没有业务丢失时，不新造 eventId。原生 drain 把 handled 视作终结，因此不能先 handled 再把入站仅放内存，DSH 不可用时不能静默吞消息。

[入站监控 API](https://github.com/openclaw/openclaw/blob/04fefb3455a0b0779909b251dbabb19f4d61db29/docs/plugins/sdk-channel-outbound.md)已有 createChannelIngressMonitor/createChannelIngressDrain/openChannelIngressDrain，优先接它们的持久与恢复生命周期；是否被每个选中插件的每类事件实际使用仍需逐路径核查。我们不自写第二套通用消息代理。

### 出站与实际 scope

已核 [Gateway send handler](https://github.com/openclaw/openclaw/blob/04fefb3455a0b0779909b251dbabb19f4d61db29/src/gateway/server-methods/send.ts)的实际方法名是 **send**，入参包括 channel/accountId/to/message/replyToId/threadId/idempotencyKey；**chat.send 会进入会话派发，不用它代替平台发消息。** [core-descriptors.ts](https://github.com/openclaw/openclaw/blob/04fefb3455a0b0779909b251dbabb19f4d61db29/src/gateway/methods/core-descriptors.ts)将 send 列为 operator.write；这不是仅限某个接收人的窄权限。需经桥限制渠道账号、目的地、payloadHash、Effect 和有效授权，不能把宽 Gateway 凭据交给 replyer。

另有 [channel-outbound](https://github.com/openclaw/openclaw/blob/04fefb3455a0b0779909b251dbabb19f4d61db29/docs/plugins/sdk-channel-outbound.md)的 sendDurableMessageBatch/withDurableMessageSendContext。本地桥可通过受认证专用入口调用这些公开能力；**专用桥入口和查询台账是设计中的适配，不是 OpenClaw 自带的 shiyu.send/queryReceipt API。** Gateway 的 idempotencyKey 已有处理，但本轮未证明外部 RPC 在所有断电窗口有跨重启持久去重，不能凭字段名承诺恰好一次。

Effect 是逻辑动作权威；sidecar 的 delivery intent 是其传输子记录，只有一个组件负责同次原生发送的重试。首次收到 Effect 先持久绑定 effectId+payloadHash 与发送 intent，再派发；同键异内容拒绝。OpenClaw 返回 OUTBOUND_DELIVERY_QUEUED 时只记录待核对，不再次走 SDK 补发；sent/partial_failed 要保留所有子消息回执，超时或无平台身份为 unknown。下游实际派发及重放前仍验证 Mandate、代次、撤权/删除水位。若无法在侧车内部重试点重新校验，就不启用延迟自动发送，并把该模式列为验证不通过。

## 三个平台分别如何复用

### WhatsApp

OpenClaw 的[固定说明](https://github.com/openclaw/openclaw/blob/04fefb3455a0b0779909b251dbabb19f4d61db29/docs/channels/whatsapp.md)明确是 **WhatsApp Web / Baileys linked-device**：二维码关联账号，网关维护会话，凭据/连接状态写本地；不是 Meta Cloud API，也不是独立 Twilio WhatsApp 渠道。复用完整插件的价值在连接保活、QR、媒体、群与目录处理；直接复制 send 函数不能得到这些生命周期能力。Baileys 是独立开源实现，MIT 不等于 Meta 官方服务许可；账号登录/平台兼容与凭据恢复风险单独验证。

**官方业务路线是 WhatsApp Business Platform Cloud API**，Meta 的[官方 Postman 工作区](https://www.postman.com/meta/whatsapp-business-platform/overview)明确提供业务系统收发 API。它使用业务账号/号码、令牌、webhook 与业务消息政策，不等同个人号全部聊天或群访问。主动通知要依实际模板/会话窗口/接收方许可校验；不沿用 Web 路线假设。Meta 文档本轮抓取遇到 429，具体实时额度/定价/账号能力未复核，不写死数字。已有 Meta 官方 API 或服务商适配可作这条路线，不把 OpenClaw 当前 WhatsApp 插件冒称官方 Cloud API 连接器。

### QQ

官方机器人优先复用腾讯[qqbot-nodejs USAGE.md](https://github.com/tencent-connect/qqbot-nodejs/blob/429a0f1b798f3b0fcef3679e207dbc0469a1df2d/USAGE.md)：new QQBot、on('message')、start/stop、sendText(msg.replyTarget,text)。SDK 已处理 token 缓存/刷新、WS 心跳、RESUME/IDENTIFY、关闭码重连、部分上传重试，并有 sessionPersistence 接缝；无需自己实现协议。高层 replyTarget 主要覆盖 C2C/group，guild/dm 需底层 MessageApi。msgId 有值表示被动回复，无值走主动消息且受平台额度限制；本轮官方额度页面不可访问，不承诺无限主动推送。

统一侧车可直接装腾讯官方 OpenClaw QQ 插件以复用现有整合；SDK 直连则复用相同底层成熟能力，减少 OpenClaw runtime 依赖。两条都不等于个人 QQ 登录：Bot AppID/AppSecret、OpenID 与个人号好友/群不同。扫码开通机器人不证明接管用户原个人账号。

个人 QQ 的 NapCat/OneBot 等另立实验候选。本轮限定查到 [NapCat 固定许可证](https://github.com/NapNeko/NapCatQQ/blob/98d781d19815d1625b24d717ce280ecf0a4f6d0c/LICENSE)为自定义 Limited Redistribution License，包含商用/修改分发限制；不能按 MIT 复制或当腾讯官方 API。当前方案不将其作为默认依赖。

### 飞书 / Lark

OpenClaw 飞书插件有私聊/群、WS/Webhook、媒体/卡片/流式和工作区工具；只做连接时停用文档/wiki/drive 等无关工具注册与权限，不能因插件名称就开放内层写权。

官方 SDK 1.76.0 已有[高层 Channel](https://github.com/larksuite/node-sdk/blob/b188be60134d409b61259546bcf69c731d2b0b7c/docs/channel.zh.md)：createLarkChannel、on('message')、connect/disconnect、send/stream；处理传输、归一化、策略、重连、媒体上传和卡片。底层 Client/EventDispatcher/WSClient 仍可直接使用。**不要把直连方案误写成自建 WS/格式/重连。** NormalizedMessage 有 messageId/chatId/chatType/resources/mentions/threadId 等，senderId 可能从 open_id 回落到 user_id/union_id，适配必须保留身份类型和 app/tenant 命名空间。

必须审核其默认行为：内部 dedup/stale/并发锁可静默丢弃，不能替代识雨持久接纳；send 的 target_revoked 可自动去掉 replyTo 重发、format_error 可改纯文本重发，副作用和格式变化必须纳入 Effect 计划。若配置不能约束，使用 rawClient 的明确单次发送或最小适配补丁，不凭空声称开关已存在。媒体先转受控对象，不把用户提供路径直接交给 SDK 的本地文件读取。流式占位卡会在最终门禁前产生发送，首轮仍用完整草稿后发送。

## 聊天队列的具体做法

```text
平台/侧车传输队列（可选、仅传输）
  → DSH 持久 inbox + IntakeReceipt
  → ConversationService：会话序号、代次、待答集合
  → p-queue：有界模型执行槽
  → replyer：answer 或 needs_core
  → 发送门禁 → Effect/outbox → 渠道原生投递 → Receipt
                       ↘ core → TaskService/worker → 状态事件/只读视图 ↗
```

1. **先落盘再排队。** 接纳事务校验来源/身份/大小、持久事件及 sourceEventId 去重键、分配 conversationSeq；p-queue 里只放 turnId，不把内存任务当恢复真相。
2. **同会话串行，跨会话公平。** conversationKey 包含稳定 connectionId、原生平台会话、受众，并按平台声明包含 thread；connectionId 绑定 provider/tenant/app/服务账号，重连不变；不同账号或同名群不合并。每会话最多一个生成任务，每次只把一个候选放全局 p-queue，完成后有后续则排尾。模型仍共享全局 3 槽、后台最多 2、对话预留 1，不为渠道再增一套模型预算。
3. **突发合并有边界。** 同主体同受众未开始文本可在 250 ms 内合并，保留各 eventId；控制/删除/编辑各有语义。每会话待答 20、总 1000 是待验证上限，满则明确背压或 gap，不静默丢弃。
4. **新纠正让旧结果失效。** 原子推进 conversationGeneration，再 AbortController 取消旧模型；旧调用不响应也无权发送。未答输入保留后重新取视图；认证停止/撤权走控制入口，不等模型队列。常规输入到底合并/替换/保留逐条按消息类型确定，不让模型凭感觉改队列。
5. **普通问答不必唤醒 core。** 程序可用受众限定 ReadView 直接 replyer；需要行动/长期变更/目标判断才转 core。replyer 返回 needs_core 只是升级提示，以原 eventId 一次去重，不能产生 TaskSpec/Mandate 或循环重投。后台 Task 与聊天队列独立，状态查询不被长任务卡住。
6. **表达和发送分开。** 完整 ReplyDraft 生成后检查授权、受众、conversationGeneration、authEpoch、tombstoneWatermark 与目标/任务停止；统一 Effect.origin=dialogue 及稳定幂等键。只有 Receipt 证明的平台接纳才报告发送；未知状态先核对，不能让第二个队列继续盲重试。
7. **重启恢复。** 从 inbox/DialogueTurn 重建内存执行引用；无可靠草稿的 generating 重新排，ready 重新过门禁，已 dispatching/unknown 发送先核对。Effect 与 sidecar intent 不双重派发。

OpenClaw 飞书[sequential-queue.ts](https://github.com/openclaw/openclaw/blob/04fefb3455a0b0779909b251dbabb19f4d61db29/extensions/feishu/src/sequential-queue.ts)超时会放行同 key 下一项但旧任务继续运行，不能复制后宣称严格无重叠。p-queue 超时也不意味着正在执行的操作被终止；conversationGeneration 与真实发送门禁保留。
