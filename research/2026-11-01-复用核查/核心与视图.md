## 3. 依赖闭包、许可与接入方式

补充 R7：[DSH Goal README](https://github.com/deepseek-ai/deepseek-harness/blob/ce7073d51254c26cd63b22a60835b8f948deb447/packages/goal/goal/README.md) 与 [包清单](https://github.com/deepseek-ai/deepseek-harness/blob/ce7073d51254c26cd63b22a60835b8f948deb447/packages/goal/goal/package.json) 已静态阅读。`ctx.goals.get(agent)` 返回 detached view，create / edit / pause / resume / complete / block / clear 使用 GoalRef `{id,revision}` CAS；只接受 exact live Agent，需 sessionProjections，Session log 是唯一目标状态权威。每 Session 一个 currentGoal，active / paused / blocked / complete 四阶段；恢复后 active 为 disarmed。服务不调度，不提供费用预算或独立完成认证。

接入决策：一持续目标一个专用 Session，控制库只留会话映射和范围 / Mandate / 时间 / 费用元数据；普通单轮请求不用 Goal。多目标不硬挤同一 Session。取消 / 到期是控制原因与 disarm / clear 映射，不另造同名 Goal 状态库；暂停轮次另调用 Agent.cancel，生命周期与实际效果停止分开核对。验证多 Session 成本、恢复无自动授权、终态不能被普通 followup 重开；失败先限制同时激活目标数，不直接另写目标引擎。Goal 包版本同为 0.2.2-alpha.2、MIT；运行依赖 schemastery 与 zod 4.4.3，peers 为 agent / session-projection / brand / llm / scope / session / typert-protocol / Cordis，沿用同宿主依赖闭包。

### DSH：直接调用宿主公共包

固定包版本为 `0.2.2-alpha.2`，必须与同一宿主提交的依赖组合验证。`@deepseek-ai/dsh-agent` 运行依赖 `@deepseek-ai/dsh-brand` 与 `zod 4.4.3`，通过 peers 使用 llm、scope、session、session-projection、system-prompt、协议 / util 与 Cordis 等宿主服务；不独立复制其默认 loop。scope 本身无额外运行依赖，依赖宿主 Cordis peer；system-prompt 使用 `@deepseek-ai/schemastery` 并以 peers 接 llm / scope / Cordis。以各固定 [agent 清单](https://github.com/deepseek-ai/deepseek-harness/blob/ce7073d51254c26cd63b22a60835b8f948deb447/packages/core/agent/package.json)、[scope 清单](https://github.com/deepseek-ai/deepseek-harness/blob/ce7073d51254c26cd63b22a60835b8f948deb447/packages/core/scope/package.json)、[system-prompt 清单](https://github.com/deepseek-ai/deepseek-harness/blob/ce7073d51254c26cd63b22a60835b8f948deb447/packages/core/system-prompt/package.json) 为准；不只安装孤立包名后声称兼容。

### DS-Bot：只复制已核查的纯函数闭包

计划复制 `btw.js` 中 `callIds` 与 `trimToolBoundary`，依赖仅内建 Array / Set 与消息字段，不带 fs、path、卡片存储、BlockAssembler、install(rt) 或 callAside。输入须先经过会话授权；该助手仅平衡尾部工具消息，不负责 ACL、删除或角色隔离。固定来源代码尚未复制，验证阶段将其放在隔离测试目录并记录修改。

## 4. 产品规则与分域一致性

1. **core 的必要规则**：当前用户目标、允许资源、通知静默、调用预算、暂停、来源可用性、领域命令白名单。DSH 的 Agent 生命周期不替代这些规则；Superagent 的编码任务流程也不能自动授予识雨全设备权限。
2. **views 的必要规则**：purpose / actor / channel 限域、来源 ACL 与 tombstone 过滤、字节 / 条目上限、新鲜度、发送前重新检查。DSH scope 只管理注册作用域；冻结 Session 是对话历史快照，不是六域授权视图。
3. **控制账本不是所有数据的物理所有者**：`commitSeq` 只证明控制库事务位置；`stateVersion` 是已发布的内层组合投影版本，不能包装成 Ombre CAS。根契约 `ReadView.components[]` 记录 backendId、componentRevision?、verifiedSourceHash?、capturedAt、indexVersion?、freshness；hash 不是 CAS。不存在的版本保证必须明确为空 / 不可证明，不能用时间戳替代。
4. **跨组件失败可见**：控制库提交意图并不说明 Ombre 已写入。根契约 MemoryOperation 使用 approved → dispatching → applied / unknown / rejected，只有 applied 有已核对的后端效果。未知结果先查组件证据再继续；没有已验证幂等能力时不盲重试。跨记忆 / 关系依赖尚未全部确认时，阻断需要该一致结果的任务；允许显示已核实的部分进展，不谎称原子提交。组件删除未完成时先由控制删除屏障阻断查询与旧草稿。
5. **未来分域兼容**：使用领域读写端口与真实组件回执，不以统一 SQLite 连接当接口。采用根 v1.1 公共契约；本专题不自创另一份 pending / unknown 枚举或事务框架。分域能力未验证前保留单库对照，不能把对照默认优势写成用户要求。
