# 数据空间：已有组件复用核查

日期：2026-11-01。覆盖 `state / task-store / evidence / artifacts / cache / config / credentials / checkpoint` 与 `data` 区域。证据为一手资料与限定源码静态核查；**未安装、未运行、未复制代码到产品，未创建数据库、卷、服务或凭据**。以下是下一阶段优先验证的接入方案，候选未升级为已经实施。

## 结论与替换范围

优先验证 **Superagent 局部控制账本 + Ombre 单一记忆后端 + 组件原生导出 + 系统凭据设施**。取消「先自写所有 Repository、Task 物理表、记忆对象 / 媒体 / 导出格式，然后把现有项目当参考」的默认计划。单库不是用户要求；不能因 Ombre 使用 Markdown / Python / 多库就拒绝复用。

保留本地 SQLite + FTS5 路线作为可比较的回退：它的跨聚合短事务优势真实存在，但不意味着组件路线必须伪装为同库原子。DSH 的独立记录仍可直接用 storage-domain；任务已存在 Engine / Store 时优先复用其聚合，不把所有状态塞进一个无限增长的大 JSON 只为获得单记录 put。

## 复制闭包与必要补丁（计划，尚未复制）

1. **任务域**按任务专题复制 `src/core/{engine,part,model,ports,ids,errors,reasons,intake,evals,tickets,assignments,replies,stage}.ts`。该运行闭包只需本地 core 与 node:crypto。保留原文件归属 / MIT；TaskService 只是识雨产品适配，不另造一套同职责 Engine。
2. **Store**抽 `atomic / afterCommit / depth / committed`，及确实使用的 triggers / threads / tickets / decisions / receipts 与相关 DDL / generated columns；不连带复制全套 Settings / source / schema10→11 迁移。KV 通用键与 Versions 单独按配置需求复用。若这些提取迫使大量改写，下一阶段先报告实际 diff 和维护量，不以“薄”字掩盖规模。
3. **事务必修**：现源码先增加 depth，再在 try 之前 SAVEPOINT；SAVEPOINT 失败可能留下错误 depth。ROLLBACK TO / RELEASE 失败也需保留原错误并隔离连接。采用宿主已有错误处理模式补 start / rollback 边界；同步回调不得返回 Promise，网络与模型不在事务内。V14 必须覆盖 savepoint 创建失败、内部回滚失败、嵌套回滚和提交后回调异常。
4. **效果必修**：generation 解决旧回调覆盖，不解决任意外部 exactly-once。补 replayClass、当前授权复核、unknown 和 operation 查询；只对确认幂等的动作自动重试。上游 outbox receipt 最小身份与识雨 TTL / 删除政策对齐，不能删去重身份后导致老输入重新执行。
5. **Ombre**优先作为原组件调用 SourceStore / MediaStore / backup_archive，不为 TypeScript 宿主重译 Python。hold / grow / trace 是否已有公共 operationId、expectedRevision、去重查询仍需核实；them 的局部 expected_revision 不能证明全体接口具备 CAS。只有真实接口或局部服务端补丁经验证后才能启用相应写操作。

上游补丁需记录固定来源、文件、用途、局部 patchDigest 与原测试映射；升级先重放复制代码差异和 V06 / V12 / V14 / V16 / V22。不得因上游分支更新就悄悄替换已验证代码。

## 最小跨组件一致性契约

- 控制库 `commitSeq` 只表示其本地成功事务；`stateVersion` 表达已发布组合投影版本。Ombre 的 revision、来源 hash、indexVersion 和捕获时间另存，不虚构跨服务单调总序号；源 hash 仅核对，不是 CAS。
- `component_operations` 是逻辑目录，记忆分支使用公共类型 `MemoryOperation`；至少表达 operationId、proposalId、backendId、commandType、expectedComponentRevision、payloadRef、status、attempt、resultRef、lastObservedAt；同事务写批准记录与 outbox。网络调用后核对结果，状态 approved → dispatching → applied / unknown / rejected。只有 durable 本地记录还不足以保证后端幂等。
- 无后端写条件时，本库 CAS 无法保护后端另一写者；必须控制所有写入口或在后端增真正条件更新。无幂等查询时，发送后超时进入 unknown 并暂停依赖动作，不能盲目重发记忆写入。
- ReadView 带 control 水位与 components[{backendId,componentRevision?,verifiedSourceHash?,capturedAt,indexVersion?,freshness}]。查询后复核 authEpoch / tombstoneWatermark；相关操作 pending / unknown 或版本不符时，回带 stale / pending。返回组件片段可以具有不同 capturedAt，但不得称为同一时刻的完整内部状态。
- 源删除先在控制入口拒读，随后确认 Ombre 桶 / 原文 / 媒体 / 索引 / 导出与缓存的清理；hash 和可重识别摘要也清除。最新删除水位未知的恢复实例不开放模型上下文。此屏障是识雨策略，不是组件原生删除已经满足的事实。

## 现成备份的实际边界

`backup_archive.py` 的 `build_export_archive_file` 逐文件流式压缩并记录 hash / 大小；`_snapshot_sqlite_to_file` 调用 Python sqlite3.backup，快照后 quick_check；覆盖 embeddings 与存在的 You / them 库，导出来源闭包校验已见源码。`extract_backup_archive_file` 复用成员大小、路径、manifest 验证；不用自行重写 ZIP 校验。

但它不是所有文件 / DB 的全局事务：Markdown 和多个库依次取样；导出路由锁不证明 dream / decay / write 等写者停住。组件 manifest 也不自动包含识雨控制库和删除账本。顶层 Bundle 记录 components[{componentId,snapshotRef,manifestSha,watermark,quiescenceEvidence}]、在途操作与 reconcileRequired；恢复后核对映射和应用结果，再打开读取。

现有导出总解压上限 512 MiB，测试先让 Ombre ≤256 MiB；总1GiB目标可由其他通用对象构成，不能声称原接口已支持1GiB记忆归档。临时文件默认系统 temp；受控 TMPDIR 或外置路径盘点须验证。媒体是否完整进入导出仍待专门验证，不用“有 ZIP”替代恢复覆盖率。captureTime 取必要组件最早捕获时刻；外置副本成功时间不能冒充数据新鲜度。
