## 3. Engine 的精确复制闭包

生产闭包为 `src/core/` 中 `engine.ts`、`part.ts`、`model.ts`、`ports.ts`、`ids.ts`、`errors.ts`、`reasons.ts`、`intake.ts`、`evals.ts`、`tickets.ts`、`assignments.ts`、`replies.ts`、`stage.ts`。这 13 个文件的运行时依赖限于彼此及 ids.ts 的 `node:crypto`；不依赖 DSH 或 SQLite 实例。应直接导入所需文件；原 `index.ts` barrel 还导出 `memory.ts`，不要无意扩大生产闭包。MemoryRepositories 可作为单独的测试夹具复制。

入口与端口见 [engine.ts](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/src/core/engine.ts)、[ports.ts](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/src/core/ports.ts)。接入保留 `receive / evaluateDue / decide`、输入确认与 handback、Assignment 事件等既有实现。Repositories 接 task store；Policy / SourceScope 接当前 Mandate；Executor 接 DSH 受限执行适配；Outbox 接统一 EffectDispatcher；时钟使用注入值，便于到期与恢复验证。业务侧不再调用另一套平行调度器。

Engine 在领域命令的事务中调用 Executor.start / deliver / stop 与 Outbox.send；这些适配方法只能同步写入 effect，不可直接启动模型、取消真实设备或发消息。Repositories.triggers 还包含 disposition 及线程关联访问，复制仓储时须包含对应 `disposition / trigger_thread` DDL，不能只按四个主表名裁剪。上游 Outbox.status 的 ReplyStatus 只有 pending/sent/dropped；识雨的 dispatching/unknown 在此窄端口保持 pending，同时由独立 Effect 事实阻止再次派发，不能错误投影成 sent/dropped。

需要明确的小范围语义补丁：

1. [intake.ts](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/src/core/intake.ts)、[tickets.ts](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/src/core/tickets.ts) 的 wake、Engine.evaluateDue 的终态补充消息唤醒必须加显式策略门。识雨普通追问不能复活终态；明确重做创建新 Task，并关联旧 Task。非终态任务仍使用上游输入归属、等待及继续机制。
2. [assignments.ts](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/src/core/assignments.ts#L79) 的 `interrupted` 会自动 restart 或 deliver。由唯一 TaskRecoveryCoordinator 先核对未知效果、旧实例及资源；屏障通过后才允许 `Engine.assignmentInterrupted`。不要另写第二个任务恢复状态机。
3. 上游 ready report 可以结束 Ticket。识雨将其作为“执行报告已到”；ResultVerifier 的 completionSpec 检查才允许公开 Task.succeeded。未知效果事实优先映射 unknown，不能被上游 waiting / ended 覆盖。Task 七态、Assignment 三态保持[总契约](<../../架构与设计/A方案全景/跨模块契约.md>)；内部 Ticket 状态无需强改为同名字段。
4. 在仓储适配及派发门处增加当前授权、安装代际、hostEpoch、单调整数 fencingToken、聚合 CAS 与取消标记；复制的队列 generation 只防旧队列回调，不等于设备 fencing。

因此保留的是可工作领域实现及其测试结构，不是仅借用几个名称。补充字段可存 task extension 记录，与原 Ticket JSON 同事务；无需先把整个领域重新正规化为自创表集。

## 4. Store、Effects 与 Outbox 的复制范围

### 4.1 Store：复制事务内核和所需仓储，不整抄应用配置

[`src/app/store.ts`](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/src/app/store.ts) 使用 DatabaseSync、SAVEPOINT、afterCommit、JSON 仓储及 SQL 索引。选择复制 `atomic / afterCommit`（约 L134–161）、trigger/thread/ticket/decision 的 CRUD、receipt 仓储和它们依赖的 DDL、generated columns、索引及 JSON helper。原 Store 整文件还依赖 `kv.ts / policy.ts / migration.ts / versions.ts / store-read.ts / core`，因此不把整文件称为独立事务库；Settings、schema 10→11 的业务迁移和管理视图不随片段带入。新组件命名空间和 schema 版本迁移由数据专题统一，DDL 与 CRUD 必须同一补丁维护。

该选择直接使用原有事务机制与仓储，不另造一套 UnitOfWork 库。CoreCommitService / TaskService 以受限领域命令进入这一事务边界。Task、Assignment 补充记录、Effect 与 outbox 在任务账本同一事务；记忆后端若采用 Ombre，则跨库提交是独立 CommitReceipt 与重试核对，不能声称整个识雨内层和任务库天然原子提交。

复制前必须修正已静态发现的失败路径：

- `atomic<T>(operation: () => T)` 允许 T 为 Promise，但原实现会在异步完成前 RELEASE。接口限定同步领域命令；运行时拒绝 thenable 并回滚是额外防误用，不能依赖它停止已经发起的异步活动。网络、模型及设备调用一律不进入事务回调。
- 原代码在 SAVEPOINT 执行前递增 depth；SAVEPOINT 失败位于 try 外，可能遗留错误嵌套深度。补丁需在建立成功后提交局部栈状态，或在所有入口失败路径恢复。
- ROLLBACK TO / RELEASE 本身失败会掩盖原始错误且缺乏隔离。保留原始与清理错误，核验事务状态；不能确认时关闭派发并隔离数据库连接，禁止继续接受写命令。借鉴宿主 SqliteKvUnit.write 的 unknown-state 隔离处理，详见[宿主复用核查](<宿主与依赖.md>)。
- afterCommit 仅为内存回调，进程崩溃会丢。只用于唤醒扫描；可靠工作必须先记录到 Effects。同一嵌套事务回滚时不能执行其 afterCommit 回调。

### 4.2 Effects：保留队列算法，补充结果分类

[`src/app/effects.ts`](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/src/app/effects.ts) 可复制完整队列 class 及 `Later`，使用窄 Store / Health 适配。保留 SQL 持久入队、kind/key 去重、seq 排序、generation 防旧回调、每 kind 并发上限、退避、start / idle / drain 实现；HealthBoard 在此是类型依赖，不需要带入整套管理 UI。

原队列成功后删行、异常默认重试；`cancel` 删除行不意味着运行中操作停止。补丁在 handler 前持久登记 dispatching 与 attempt，按确定可重试 / 延后 / 确定失败 / unknown 分类；unknown 冻结重放并进入查询。持久 Effect 结果另存账本，成功删除队列行不删除证据；取消保留在途身份与停止标记。恢复屏障通过前不 start。这样保留已有调度代码，只修改会破坏识雨效果保证的路径。

### 4.3 Outbox：保留事务发送和收据，替换渠道端口

[`src/app/outbox.ts`](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/src/app/outbox.ts) 约 58 行，运行依赖为 Effects.Later、infra/text 的 checkedImText 以及注入 Store/SourceRegistry 等对象。复制其 send / status / withdraw / deliver 逻辑与 Store.receipts；将 SourceRegistry 收窄为 send / queryReceipt / allowed 端口，不引入 GitHub / 飞书业务链。[infra/text.ts](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/src/infra/text.ts) 无第三方依赖，但原 IM 字数限制应改为渠道配置，不能作为所有消息的产品规则。

必要补丁：相同 ID 比较 payloadHash；发送前重查 Mandate、目的地、origin 与对话 generation；超时 unknown 不进入默认重发；receipt 保存真实 providerMessageId；withdraw 不能把在途效果宣称撤回；现有 `receipts.behind` 按 ticket/channel 排序，对 dialogue origin 改为 conversation/channel，且不能越过较早的未知发送。清理正文时保留覆盖允许离线/重试窗口的最小去重身份，不永久保留完整私信。

## 5. Worker 的最小复用闭包

[`src/executor/dsh.ts`](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/src/executor/dsh.ts#L171) 的 `WorkerSlots` 只依赖 Map、running/max 回调与 Later，适合从大文件抽取。保留预留槽、启动与唤醒竞争的实现；上游 person 路径额外 1 槽须计入宿主全局预算或明确预留控制槽，不得无预算扩容。副作用能力仍受资源互斥限制，槽位不是授权。

[`src/executor/background.ts`](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/src/executor/background.ts) 的运行依赖为宿主 jobs / subagents 接口、计时器等，可复制需要的 `until / runningJobs / collectJob / killJobs / stopBackground / stopSubagents / untilQuiet` 工具；通过接口兼容验证后使用，不另写后台收敛循环。它们只报告停止流程，不保证远端物理动作停止。

完整 DshExecutor 还依赖 worktree 准备、Settings、sessions、notices、environment、Effects 及业务上下文；完整 sessions.ts 又绑定模型角色配置、skills/prompts、工具集合等。当前直接使用 DSH `ctx.agents.create` 与 setup 限权，抽取上述已隔离部分收益更明确。若验证时完整 executor 的端口替换反而显著更小，可以比较补丁量后改用它，但不能默认带入宽工具与 Git 项目生命周期。

精确恢复接点是 `DshExecutor.resume`（L524–536）→ `Engine.assignmentInterrupted` → `Assignments.interrupted`；并非存在一个可直接调用的 core.bootstrap。宿主恢复入口只调用唯一 TaskRecoveryCoordinator，不能与原 resume 同时自主派发。

## 6. 备选、维护与验证门槛

整包安装 Superagent 能保留最多上游代码，但会引入其 GitHub、渠道、主会话、工作区、Settings 和权限默认，且 A 已有 DSH 插件角色边界；局部复制纯域+队列能少带入这些业务依赖，因而是主方案。自己重写小 TaskService 没有收益证据，退为不选。单独状态机库只替代转换表，不能同时取代已有仓储、输入归属和 outbox，因此本轮不增加依赖。

若以后确需多中心持久调度、跨站点长流程及版本化重放，评估成熟 [Temporal Workflow / Activity](https://docs.temporal.io/workflows)：它可承担调度与历史，但仍要处理 Activity 副作用与识雨授权、设备幂等。迁移时独占 Task 派发权，禁止两套调度器同时执行。当前单中心 A 已有可复用实现，尚无为此新增 Temporal 服务或 Redis 队列的需求证据。

源码副本维护采用一个固定来源清单和顺序补丁集：权限 / 恢复语义、事务失败、结果与 unknown、宿主适配分别记录；升级逐文件比较，先跑保留的领域测试再跑识雨 V10/V11/V12/V14/V23。若新版本兼容失败，保持上一个已验证副本，不悄悄换成自写引擎；若首次验证无法补齐必要边界，只开放无副作用替身，报告明确失败项后比较其他现成编排方案。

验收最低要求：V10 覆盖撤权/预算；V11 50 个领取竞争、旧 fencing、暂停恢复、后台停止和禁终态自动复活；V12 所有事务/派发/外部成功/回执断点及 unknown；V14 SAVEPOINT 入口失败、嵌套回滚、回滚/释放失败隔离、误传异步回调不提交；V23 Task 成功、记忆提交拒绝、消息未知可以同时准确展示。固定任务七态与 Effect.origin 保持不变，无总契约状态修改请求。
