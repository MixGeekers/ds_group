## 1. OS 监督及最小 RunGate

**固定证据：**Apple launchd 开源快照 `d448a1c8f70a61202f8705f94337f686b87c30c4`（launchd-842.1.4，历史源码），[launchd.plist.5](<https://github.com/apple-oss-distributions/launchd/blob/d448a1c8f70a61202f8705f94337f686b87c30c4/man/launchd.plist.5>) 的 `SuccessfulExit`、`ThrottleInterval`；[Apple 官方登录服务说明](<https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/CreatingLaunchdJobs.html>)。使用目标系统自带程序，不复制 Apple 源码；历史源码不能代表本机版本，验证须记录 macOS build 与本机手册。此次未证实该历史树的许可证文件路径，不计划分发它。

Linux 对照固定 systemd **v262**：[服务接口](<https://github.com/systemd/systemd/blob/v262/man/systemd.service.xml>)、[许可](<https://github.com/systemd/systemd/blob/v262/LICENSES/README.md>)。项目默认 LGPL-2.1-or-later，配置示例 MIT-0；计划只使用系统服务接口，不复制守护代码。直接配置 `Restart=on-failure`、`RestartSec`、`StartLimitIntervalSec`、`StartLimitBurst`；支持通知协议后才用 `WatchdogSec`。不需要为了监督 DSH 引入 PM2/Kubernetes。

RunGate 仅接收固定 StartManifest，读取 RunIntent、持久预算并映射退出原因。launchd 缺少识雨跨重启的总预算与业务停用语义，这部分仍需适配；Linux 原生 rate limit 能覆盖正常重启额度，但持久停用、safe-mode和跨备份代际仍需业务控制记录，不能同时维护两套竞争的计数器。由一个预算源给出是否可启动，OS 限流只作额外上限。10 分钟最多 5 次自动启动包含 safe-mode，绝无第 6 次追加机会。

[Superagent runtime.ts:90–98、228–250](<https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/src/app/runtime.ts>) 已用 `proper-lockfile` 的 `lockSync`，先锁 stateDir 后开 SQLite，shutdown 先 close 再 release。优先由宿主生命周期单一持有该锁，RunGate 不再自写 PID 锁。[依赖版本](<https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/package.json>)固定 4.1.2，[proper-lockfile MIT 许可](<https://github.com/moxystudio/node-proper-lockfile/blob/v4.1.2/LICENSE>)。可局部复制生命周期调用顺序与错误清理，保留 Superagent MIT 声明；不复制其整个 Runtime 及 GitHub/飞书/面板依赖。上游 `stale:30000` 不是跨机器 fencing，长暂停/睡眠与锁丢失需 V21；compromised 后先停止业务和关闭数据库，不能以锁过期证明旧写者已消失。

## 2. Ombre 已有导出、导入与原子边界

固定 **3.6.14 / `115d831d979bf67efc7150f976e2cb34c333c935`**，Python 服务，MIT；[LICENSE](<https://github.com/P0luz/Ombre-Brain/blob/115d831d979bf67efc7150f976e2cb34c333c935/LICENSE>)版权 2026 P0lar1zzZ，复制实质代码需保留许可与版权。优先在所选 Ombre 服务中直接调用，不为单个备份函数额外引入完整 Python 服务。

| 既有精确入口 | 已静态核查能力 | 接入与缺口 |

**重要边界：**导出先逐个读 Markdown / source，再依次备份多个库；未见跨全部写者的共同冻结。每库一致、每文件正确不能推出同一时间点的全局一致。采用 Ombre 时由数据模块唯一 CheckpointService 协调 ledger、Ombre 和对象。优先在停止所有 Ombre 写者/后台任务的受控窗口调用导出；若不能证明已静默，只可记录组件快照向量，保持 `reconcileRequired=true`，不能声称 atomic 或直接开放读/派工。主存储不强制单库，恢复必须核对跨组件写入回执。

组合包增加 `components`：组件 ID、版本、快照引用、内部 manifest 摘要、组件水位、静默证明/恢复要求。由数据模块生成并最终发布 ready；backup-copy 只读取，不重新实现其闭包或扫描活跃源。Ombre 当前生产导出/导入总解压上限 **512 MiB**；V22 组件夹具先设 ≤256 MiB，总 1 GiB 可以含其他对象。大于限制需明确改 `MIGRATE_MAX_TOTAL_UNCOMPRESSED_BYTES` 及对应导出/导入资源预算、磁盘检查和测试，不悄悄移除限制；不是本轮已打补丁。

终检补齐 DSH Goal 权威闭包：根据宿主/任务域以 Session log 为 Goal 权威的复用决策，`dsh-goal-sessions` 是必需 component。由数据模块唯一 CheckpointService 收集 GoalBinding 绑定的目标专用 Session 耐久日志、必要 projection 定义/配置，记录实际 log seq、GoalRef revision、原生 phase/armed 与 DSH/plugin/projection 版本；通过受控 flush 或静默/停宿主闭合复制后核对，不能把活跃日志裸拷当一致快照。无关聊天不在范围内，缺失不能发布 ready，restic 成功也不代表业务 complete。恢复实例先关闭目标调度/派工出口、目标保持 disarmed，再核对 GoalRef/phase、本地 stop/取消、当前授权和 reconcile；旧 armed 不能自动恢复。V22/V23增加日志缺失/截断、投影版本不匹配和停用后恢复断言，失败不得read-ready或报RTO达标。这是与数据/任务域同步的设计补充，本轮未扩展源码核查或执行范围。

若未来只复制局部，最小候选是 `backup_archive.py` 的流式验证实现及相关测试，依赖闭包仍包括 `source_store` 引用解析、You/them snapshot validators和 Python stdlib；不能声称一个独立函数即可抽离。优先原服务调用，只有该闭包成本低于维护独立实现时才复制。补丁集中于写静默适配、配置临时根/限额、要求 manifest 三处；不改原有加密算法，不自行重写 ZIP 解析。

## 3. Superagent 恢复复用与必须修改的重试语义

固定 **0.1.0 / `6337fc823ce20251c8de8085948165c81aaa701e`**，MIT；依赖 Node `^22.19.0 || >=24.0.0`、DSH `^0.2.1-alpha.2`，目标 DSH 快照仍需接入验证。来源与许可证见[既有核查](<../2026-10-31-dsh-superagent/来源与核查范围.md>)。

[runtime.ts:201–217](<https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/src/app/runtime.ts>) 的初始化已有 setup → session install/ensure → executor.resume → passes/effects.start 顺序；[effects.ts:130–143](<https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/src/app/effects.ts>) 使用 seq/generation 限制旧回调，shutdown失败保留行、下次重试。可复用这些持久恢复及生命周期组件，**不能直接沿用“遗留行即再次发送”**：外部执行与本地删队列不在同一事务。崩溃发生于外部成功、本地确认前时结果 unknown。

任务 Agent 的同快照静态核查补充精确入口：`src/executor/dsh.ts` 的 `DshExecutor.resume`（524–536）遍历未结 ticket，cancel/stopWork 后调用 `Engine.assignmentInterrupted`，pending则start；`src/core/assignments.ts` 的 `Assignments.interrupted`（83–92）可自动restart/deliver。领域层没有名为bootstrap/recover的公共方法，不能虚构接口。

由任务模块维护唯一 TaskRecoveryCoordinator 和适配后的领域闭包：为非幂等效果补充 dispatching/unknown、receipt查证、取消与 fencing 校验。未知结果核对前不得调用 interrupted/start，`effects.start()` 也位于恢复屏障之后。recovery-entry 只调用其设计中的 reconcile 接口，不再编写自己的重试引擎。可查询/天然幂等动作按其证据继续，不可查询动作保持unknown；paused、撤权、取消不能通过恢复被清除。上游 Runtime 的 ready 仅说明初始化结束，不作为识雨删除/组件/任务恢复已经核对的证明。

## 4. restic 直接接入与正式恢复复用

固定 **v0.19.1**、[BSD-2-Clause](<https://github.com/restic/restic/blob/v0.19.1/LICENSE>)。使用发行二进制/CLI，不复制其 Go 加密、存储、压缩或锁实现；分发时保留许可通知，版本/校验延续[此前证据](<../2026-11-01-完整架构/恢复与备份.md>)。不引入 Borg 的并行第二仓库；Borg 是已有运维明确获益时的替代。

以下仅为未来参数化调用规格，不是本轮执行记录：`restic -r <repo> backup <ready-bundle>`；`restic -r <repo> snapshots` 固定实际 ID；`restic -r <repo> check`；完整数据检查 `check --read-data`；`restic -r <repo> restore <snapshotId> --target <fresh-staging-root>`；保留先 `forget --dry-run` 后受控 forget/prune。密码通过受信 password-command 提供，不进入日志或模型。仓库写入、锁及旧数据清理是明确副作用；验证只在合成隔离目录，未授权真实仓库前不运行。

固定文档：[backup](<https://github.com/restic/restic/blob/v0.19.1/doc/040_backup.rst>)、[check](<https://github.com/restic/restic/blob/v0.19.1/doc/045_working_with_repos.rst>)、[restore](<https://github.com/restic/restic/blob/v0.19.1/doc/050_restore.rst>)。backup exit0才是完整成功；exit3可能产生部分快照，不因有ID而通过；默认check不遍读数据。restic快照发布不把输入目录自动冻结，不能直接扫活跃ledger/Ombre目录来冒充检查点。

恢复验证同一条正式路径：restic到新根 → 组件验证器 → 最新删除/撤权重放 → 任务恢复屏障 → 兼容版本/激活核对。故障时保留已确认良好旧根，绝不直接重试写live。业务语义验收不由restic替代。删除与恢复密码管理仍由此前方案负责。

## 验证与回退

- V21：OS自动重启与用户停用、锁丢失/长暂停、含safe-mode总次数≤5；单实例无双写；失败回退手动启动。
- V22：Ombre ≤256 MiB组件 + 总1GiB组合；并发修改时验证静默证据或明确非同截面；512MiB上限、无manifest、引用缺失均明确拒绝verified；恢复失败不换根。
- V23：跨组件写入一半故障、外部成功回执丢失、停用/撤权后恢复，100个unknown不自动重发。任务和数据模块各只有一条恢复实现。
- V27：真实独立目的地与独立凭据恢复，原机不可依赖。仍用captureTime计算RPO≤15min、合成1GiB恢复只读/核对RTO≤30min；组件不一致时不得报达标。

采用状态保持已初评/建议验证；上游源码存在不等于接入成功。本轮只完成文档、源码及链接核查，没有性能或故障注入结果。
