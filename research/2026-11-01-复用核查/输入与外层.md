## DSH 可直接使用的接缝及边界

[Typert 公共契约](https://github.com/deepseek-ai/deepseek-harness/blob/ce7073d51254c26cd63b22a60835b8f948deb447/docs/subsystems/typert.md)给出 `PeerScope.principal` 在 Host 创建时固定，wire 字段不能设置；服务从 `this.ctx.invocation.peer` 读取。`@Remote` 的 resources reader 标注当前会话/目标资源；[Remote Access](https://github.com/deepseek-ai/deepseek-harness/blob/ce7073d51254c26cd63b22a60835b8f948deb447/packages/api/remote-access/README.md)处理非 owner 的角色与资源绑定、撤权失效。它对 owner 放行，因此不能替代识雨业务 Mandate、replyer 角色限制或发送前检查。入口只暴露 accept/control/status，不把任意内部提交服务导出为 Remote。

[DSH Goal](https://github.com/deepseek-ai/deepseek-harness/blob/ce7073d51254c26cd63b22a60835b8f948deb447/packages/goal/goal/README.md)已具备持久 create/edit/pause/resume/complete/block/clear 和 revision CAS，服务本身不调度。它要求 exact live Agent + sessionProjections，状态归 Session log，单 Session 只有一个当前 Goal；快照只有 objective、phase、round cap，不包含识雨 owner/scope/Mandate/多任务关系。与核心方案统一选择“一目标专用 Session + ctx.goals CRUD/revision CAS + 领域元数据”适配；业务账本只持 goalId↔sessionId、Mandate、范围和预算，不建立第二生命周期状态机。多目标通过多个 Session 映射；需验证跨存储失败窗口，不原样当成已满足多目标事务。入口只转换命令，以任务区统一适配为准。

[DSH Core](https://github.com/deepseek-ai/deepseek-harness/blob/ce7073d51254c26cd63b22a60835b8f948deb447/docs/subsystems/core.md)公开 `ctx.agents.create({...,setup})`、`Agent.send(message,target,wakeup)`、`inbox.append/replace/remove/clear`、`cancel(cause,{keepInbox})`。Inbox 有 `next-turn/next-step` 两个列表及 inserted/claimed/discarded 事件。若选择专用 Agent 路线，应直接调用这些能力；不复制 pending-list 与推理循环。pre-step 收到已经 claim 的消息，reject/omit 不保证原消息仍可消费，因此业务受理必须发生在这之前。流式模型旁路不需要创建 Agent，仅复用 LLM 接缝，业务调度采用下述 p-queue。

[Schedule 公共服务](https://github.com/deepseek-ai/deepseek-harness/blob/ce7073d51254c26cd63b22a60835b8f948deb447/packages/schedule/schedule/README.md)依赖 agents、sessions、storageDomain、sessionPersistence；按 Host 全局管理、Host 活着才能投递。调用 `create({title,prompt,timing,target},actorSessionId?,signal?)`，编辑用 expectedUpdatedAt；wrapper 限制识雨自己的 schedule ID。定时投递到专用受控入口，业务去重用 scheduleId+occurrence；不得投进通用有工具 Agent 后事后拦截。宿主保存投递回执与 Session flush 不是业务跨域事务，故仍保留 inbox 幂等与目标状态复核。

## DS-Bot 的复制单元、闭包与必要修改

### replyer 子集

来源：[btw.js](https://github.com/Fei2411/DS-Bot/blob/f823773b07ec6ca29d60b31c31af30218a68000d/ds-bot/src/host/btw.js)、[side.js](https://github.com/Fei2411/DS-Bot/blob/f823773b07ec6ca29d60b31c31af30218a68000d/ds-bot/src/host/side.js)。计划复制的单元是 `callAside` 的一次流调用/结果分类、`pairsOf` 的已完成问答排列、`complete` 的最多两次无工具问答，以及 `alive/settle/sideCancel` 的“先改取消状态，再 abort，迟到结果不可覆盖”规则。`trimToolBoundary` 可由 views 方案统一复用，避免两处维护；`snapshotOf` 不直接取得完整内部主 Session。

最小依赖：`callAside` 需要 `BlockAssembler`（直接使用 `@deepseek-ai/dsh-llm`）、`ctx.llm.stream`、受控 usage tag、准备好的消息/路由、AbortSignal；`complete` 需要 callAside、pairsOf、状态存取/存活检查、错误常量、logger；取消/封口需要受限 ConversationService 的状态更新。整个 `side.install(rt)` 则还依赖 roster、resolveAgent、botOf、chatOwners/pastOwners/groupOwners、home、文件原子替换及 load/refresh/deleteBot 包装。这些是不同层级的依赖，不能把整个文件无修改导入称为“小复用”。

必要补丁清单：

1. `callAside` 不展开原 `snapshot.header.tools`，显式 `tools:[]`，不传完整内部 toolHistory；messages 只来自已裁剪 ReadView 和当前受众近期对话。提供方/model/temperature 走已核验的宿主路由，预算由识雨当前配额覆盖。
2. 移除 `locatePrivate`、roster 和私聊自动快照，调用方提供 conversationId/turnId/conversationGeneration/viewId。`alive` 除本地存活还核查当前代次；发送前另核查授权/删除水位，模型结束不等于获准发送。
3. 把 `persist` 的 side JSON 与 `rt.save` 改为 ConversationService 局部记录；原始消息和草稿按数据保留策略处理，不写六部分内层状态。副作用仅为调用模型、usage/audit 与对话记录，实际外发只走 Effect。
4. 保留空输出、截断、工具调用、提供方错误的区分；工具调用从未 dispatch。上游 [side.test.js](https://github.com/Fei2411/DS-Bot/blob/f823773b07ec6ca29d60b31c31af30218a68000d/ds-bot/test/side.test.js)的 snapshot/no-session-write、cancel、tool retry、restart、delete/unload 断言作为后续适配测试样本；不能直接跑整个 createRuntime 测试就宣称识雨安全通过。

采用局部 fork 而非安装整个 ds-bot：其 [package.json](https://github.com/Fei2411/DS-Bot/blob/f823773b07ec6ca29d60b31c31af30218a68000d/ds-bot/package.json)只导出插件/client/web-search，没有稳定 side/requests 子路径 API；整包依赖 deep-view 与多项 DSH peers。所选函数闭包不需要 deep-view、Office、浏览器、记忆工具或群聊。每次更新上游按固定文件 diff 复审，保留迁移补丁；不静默跟随 main。这个判断基于可分离闭包，不是因为项目别处会写记忆而一概排除。

### 命名请求与发送适配

来源：[requests.js](https://github.com/Fei2411/DS-Bot/blob/f823773b07ec6ca29d60b31c31af30218a68000d/ds-bot/src/host/requests.js)。整个源模块仅 import `node:crypto`；运行闭包为 `state.requests`、`rt.own/readOnly/save/warn` 和当前进程 inflight Map。因此 `identity/verdict/known/admit` 可以按命名请求适配为统一 Effect 的幂等门禁；不需要 Bot memory 或工具注册。

必须调整：外部幂等键由程序生成并必填，payloadHash 使用 Effect 已规范化摘要，不能沿用易受对象键序影响的随意 JSON.stringify；admit 的“先 required save，再 work”映射成持久 pending→dispatching；原 delivered/uncertain 映射到真实派发的 succeeded/unknown，不能把 enqueue 成功当外部发送成功。原普通 save 会吞掉错误，改为提交 Receipt 失败时保持可核对未知状态；原 request.unsent 删除去重记录只适用于可证明未派发，不能套用网络超时。授权、目的地、代次和取消检查放在每次实际 dispatch。仅一个 Effect 所有者维护权威记录，不保留第二份 state.requests。

对于重启前 pending 的记录，先按派发证据判定；不能把“新进程”自动当已发，也不能自动重发。请求键墓碑与正文分离，回执裁剪后仍阻止旧发送复活。这个子集提供成熟控制流样本，持久事务、授权及外部回执核对是必须接入的服务。

## 队列选择与 MaiBot 比较

无工具 replyer 主路线直接依赖 [p-queue 9.0.1](https://github.com/sindresorhus/p-queue/blob/v9.0.1/readme.md)：`new PQueue({concurrency:1})`、`add(fn,{id,signal})`、`onSizeLessThan`、`pause/onPendingZero`。它提供有限并发、优先级、AbortSignal 待处理取消和排空；运行中的函数仍要配合 signal。队列只保存 turnId 的短期执行引用；业务 inbox/DialogueTurn 恢复真相仍归账本。每会话只放一个候选进全局队列，完成后把该会话后续项排尾，实现识雨需要的会话公平；不要预先把一个会话全部消息灌满队列。`onSizeLessThan` 只是等待条件，不是原子业务容量锁；接纳容量由唯一接纳器/事务控制。超时不会证明外部副作用未发生。

这替换旧文档笼统的“DSH 有限并发原语”和“必要时写小型协调器”：DSH 的 Agent inbox 解决 Agent 输入，不自动提供旁路 LLM 调用的全局配额队列；p-queue 解决通用 Promise 并发，识雨仅定义排序/失效规则。若宿主统一预算服务已采用同等成熟队列，则注入同一队列能力，不重复依赖或建立第二套额度。DSH/SDK 不兼容时先锁定兼容版或回退专用 Agent 路线，不能默认补写一套调度引擎。

[MaiBot runtime.py](https://github.com/Mai-with-u/MaiBot/blob/c6429547af711555e3d4d1b8d04b413572cb616c/src/maisaka/runtime.py)的队列是 Python asyncio.Queue；同一运行体导入 chat_manager、message_repository、global_config、工具 providers、ExpressionLearner/JargonLearner 等，并不是独立发布的队列包。只抽取 asyncio.Queue 调用价值低于直接使用 DSH/p-queue；移植整 runtime 还引入 Python↔Node 边界与状态适配。故本轮不复制 MaiBot runtime，保留其触发合并/Focus 场景作为语义比较。理由是已有同栈成熟实现覆盖且闭包更小，不是“有记忆写入所以整项目不能用”。将来若明确选择其平台生态并有显著渠道收益，再比较隔离 sidecar 与其官方平台组件，重新审完整导入闭包与 GPL v3 分发要求。

## 进入验证的条件
