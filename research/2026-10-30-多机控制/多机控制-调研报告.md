## 一、目标形态与一句话结论

**目标形态**:既有探索以 Mac 上的 DSH 宿主为背景；正式的多设备运行系统尚未建立。目标是：凡是用户授权的设备（Win/Linux/macOS/机器人），接入后识雨能像用自己的手一样使用它——执行命令、读写文件、操作桌面、管理服务，机器人则加上运动控制。

**一句话结论**:"控制多台机器"不是一个项目，而是一条五层流水线——

> **组网可达 → 特权常驻代理 → 指令下发（API/SSH）→ 各 OS 细粒度"手"（GUI 级）→ 机器人挂上同一骨架加 ROS 控制面**

每层都有成熟开源项目；**骨架首选 MeshCentral（每台设备装常驻 agent，服务级权限，REST API 可编程），最小自建路线是 SSH 密钥 + paramiko/pyinfra（零新服务）**；机器人层经 rosbridge / ros-mcp-server 并入同一骨架。

## 三、分层详析

### L1 组网层——先"够得着"

设备分散在不同网络时，第一问题是可达性。现代方案全部基于 WireGuard + 身份认证，设备只要能上网就能被到达，无需公网 IP。

| 项目 | ★ | 许可证 | 判断 |
|---|---|---|---|
| [juanfont/headscale](https://github.com/juanfont/headscale) | 45204 | BSD-3 | Tailscale 控制服务器的开源自托管实现；客户端用官方 Tailscale。**全链路可控、零托管依赖，自有设备组网首选** |
| [tailscale/tailscale](https://github.com/tailscale/tailscale) | 38360 | BSD-3 | 客户端开源、控制服务器闭源（托管服务）；不想自维护控制面时的省事选择 |
| [netbirdio/netbird](https://github.com/netbirdio/netbird) | 30373 | NOASSERTION | 定位直接写着"连接机器与 AI agents"；自托管控制面。**许可证为自定义文本，采用前须核对商业条款** |
| tmate-io/tmate | 6134 | NOASSERTION | 即时终端共享（反向 SSH），临时救急/单机快接有用，不适合做常驻骨架 |
| octelium/octelium | 4139 | AGPL-3.0 | 较新的零信任统一接入平台（组网+接入一体），观察项 |

**判断**:自有设备固定队伍 → Headscale（一台常驻小服务器，全开源）。省心优先 → NetBird（先核许可证）。

### L2 特权接入层——"拿到最高权限"的名正言顺方式

- **OpenSSH（系统自带，零安装）**:Linux/macOS 开 sshd + 密钥登录即 root/sudo；Windows 10+ 有可选功能 OpenSSH Server，另可走 WinRM。**这是最小、最透明、最能被识雨直接编程（paramiko/Libssh2）的通道**。
- **gravitational/teleport**（★21051，AGPL-3.0）:SSH/K8s/DB 统一证书接入、会话录制、RBAC、审计。设备多、多人共用、要合规审计时再加，**不是起步必需**。
- ~~hashicorp/boundary~~（★4065）:**GitHub 已标记 archived**，排除。

**判断**:起步用 SSH 密钥；把 Teleport 留作"规模/审计"增强项。

### L3 常驻特权代理层——"连上之后把它变成自己的设备"（本调研核心）

这类项目（RMM/远程管理）的共同形态：**设备上安装一个以系统服务（Windows SYSTEM / Linux·macOS root）运行的常驻 agent，开机即在线；中枢可对它做远程桌面、终端、文件管理、脚本执行**。这正是用户描述的"连上 + 最高权限 = 当自己的设备用"。

| 项目 | ★ | 许可证 | 判断 |
|---|---|---|---|
| [Ylianst/MeshCentral](https://github.com/Ylianst/MeshCentral) | 7549 | Apache-2.0 | **骨架首选**。README 原文："run your own web server to remotely manage and control computers… install an agent on each computer… a minute later the new computer will show up and you can take control of it. Includes full web-based remote desktop, terminal and file management."跨 Windows/Linux/macOS/ARM，自托管，REST API + meshctrl CLI + WebSocket，社区活跃（近 7 日有提交）。**可编程性是它区别于同类人类工具的关键** |
| [amidaware/tacticalrmm](https://github.com/amidaware/tacticalrmm) | 4526 | NOASSERTION（自定义许可，采用前核对） | 基于 MeshCentral agent 的完整 RMM：资产库、自动化任务、脚本推送、告警巡检。适合"设备队需要日常运维台账"的场景；Linux/macOS 支持较 Windows 晚，采用前按目标机型实测 |
| rustdesk/rustdesk | 127609 | AGPL-3.0 | 开源远程桌面，自建中继，装机量最大；但定位偏"人坐在屏幕前用"，对 agent 的编程接口/无人值守自动化生态弱于 MeshCentral。本机已装有（见 macOS 完全控制报告的授权记录），留给人用桌面 |
| apache/guacamole-server | 4027 | Apache-2.0 | 无客户端网关（浏览器直连 RDP/VNC/SSH）；要求目标机先开远程服务，本质是"入口聚合"而非"身体代理"，作参考 |
| fleetdm/fleet | 7080 | NOASSERTION（部分企业版收费） | osquery 系设备管理：查询资产、下发脚本、合规检测。偏"管理与盘点"，非"操控" |
| open-uem/openuem-agent | 38 | Apache-2.0 | 组件分散（console/agent/worker 多仓库）、体量小，暂不跟进 |

**判断**:
1. **MeshCentral 是最贴合目标形态的单个项目**——"中枢 + 常驻特权 agent + 全功能控制 + 可编程 API"四项全占，且 Apache-2.0 干净。
2. 需要巡检/资产/自动化任务时，TacticalRMM 在其 agent 之上加管理层。
3. 待实测项:agent 安装形态与权限级别、REST API 能力边界（下发命令/取文件/桌面流）、macOS 15+ 与 Windows 11 上的实际表现。

### L4 多机编排层——"一次指令，多台执行"

| 项目 | ★ | 许可证 | 判断 |
|---|---|---|---|
| pyinfra-dev/pyinfra | 6059 | MIT | **把 Python 代码编译成多机 shell 执行，可当库 import**——对识雨（会写代码的 agent）最顺手的批量执行方式，agentless 走 SSH |
| saltstack/salt | 15728 | Apache-2.0 | 常驻 minion（root 服务）+ 事件总线 + 实时双向，成百台规模的"神经系统"；Python 写的，识雨可直接操纵。设备多、要实时事件时上 Salt |
| ansible/ansible | 71158 | GPL-3.0 | 生态最大的 agentless 自动化；批处理式、学习资料多，作为兜底与团队协作选项 |
| rundeck/rundeck | 6350 | Apache-2.0 | Web runbook/自服务运维，人用为主，暂不选 |

**判断**:2~10 台自有机队 → pyinfra 或自研 paramiko 薄层足够；上了规模或要"事件驱动实时响应" → Salt（minion 同样以最高权限常驻，与 L3 重叠时可二选一或并存）。

### L6 MCP 桥接层——把能力挂成识雨的工具

- 既有搜索快照未找到适合直接采用的 SSH 类 MCP 项目（search_ssh+mcp.json）；这不证明不存在其他合适项目。可比较现成接口与 paramiko/pyinfra 适配层方案，主机清单、凭据与审计的设计仍待确定；不预设自建代码规模，也不依赖已删除的 vault.py。
- cua、Windows-MCP、ros-mcp-server 本身就是 MCP server 形态，宿主支持 MCP 时可即插即用;不支持时全部能力都有 CLI/REST 等价通道（MeshCentral 有 meshctrl CLI 与 REST，pyinfra 是 Python 库）——**不赌某一种接入形态**。

### L7 物理机器人层——"机器人也是 Linux"

事实前提:主流机器人主控（树莓派/Jetson/工控机/宇树等）都跑 Linux，**所以 L1~L4 的骨架原样适用**——SSH/agent 上去就是最高权限。机器人区别只在于多一层"运动控制面":

| 项目 | ★ | 许可证 | 判断 |
|---|---|---|---|
| ros2/ros2 | 6263 | Apache-2.0（分发包） | 机器人事实标准元操作系统（ROS 2），生态入口 |
| [RobotWebTools/rosbridge_suite](https://github.com/RobotWebTools/rosbridge_suite) | 1254 | BSD-3 | **把 ROS 话题/服务/动作暴露成 JSON WebSocket**——识雨不改机器人一行代码即可读写控制。机器人接入骨架首选 |
| [robotmcp/ros-mcp-server](https://github.com/robotmcp/ros-mcp-server) | 1509 | Apache-2.0 | README 原文:"connects LLMs to robots… **no changes to robot source code, just add the rosbridge node**;bidirectional: control + observe"。**AI↔机器人现成桥**，支持 ROS1/2 |
| huggingface/lerobot | 28599 | Apache-2.0 | HF 机器人库:真机驱动（SO-100/宇树等）+ 端到端学习。识雨要"学着做动作"而非逐条指令时用 |
| unitreerobotics/unitree_sdk2 | 1426 | BSD-3 | 宇树 Go2/G1/H1 官方 SDK（C++/Python DDS 直控），无 ROS 的机型走厂商 SDK |
| moveit/moveit2 | 2096 | BSD-3 | 机械臂运动规划，需要臂类精细操作时叠加 |

**判断**:ROS 生态机器人 → rosbridge + ros-mcp-server;直控协议机器人 → 厂商 SDK 由识雨在设备上编程调用;学习型操作 → LeRobot。**无论哪种，先按 L3 把它的 Linux 主控纳入统一身体管理，再谈运动控制。**

## 四、三条落地路线（供用户选择，均未执行）

### 路线 A · 代理骨架版（推荐，贴合"设备即身体"）

1. 一台常驻小服务器（NAS/云 VPS/家里旧电脑）部署 **Headscale**（组网）+ **MeshCentral**（中枢），仅内网/VPN 可达，管理面加双因素。
2. 每台授权设备装 Tailscale 客户端（指向自建 Headscale）+ MeshCentral agent（系统服务，最高权限）。
3. 识雨侧:经 MeshCentral REST API/`meshctrl` 列设备、下发命令、取文件;GUI 操作按 OS 调 Peekaboo / Windows-MCP / cua。
4. 机器人:同上接入后，其上跑 rosbridge，识雨经 WebSocket JSON 或 ros-mcp-server 操控。
5. 规模扩大后:加 Salt（实时编排）或 TacticalRMM（巡检台账）、Teleport（审计）。

### 路线 B · 最小自建版（零新服务，2~3 台设备立即能开始）

SSH 密钥 + `paramiko`/`pyinfra`（识雨自己写代码管理主机清单、执行、取回结果）+ tmux 持久会话;GUI 级远程操作用 cua/VNC。**没有任何中枢可被攻陷**，代价是没有现成的桌面流/文件管理 UI，全靠识雨自己写。

### 路线 C · 快速体验版

直接试用 trycua/cua（自托管，把已有机器注册成"agent 可用的桌面"），先验证"远程机器作为身体"的手感，再决定要不要建路线 A 的常驻骨架。

## 五、安全 · 法律 · 审计边界（与已有约定一致）

1. **只用于自有或获得明确书面授权的设备。**未授权控制他人计算机系统在多数司法辖区违法;本调研与后续任何接入均以此为前提。
2. **中枢即最高价值目标**:MeshCentral/Headscale/Salt 的管理面一旦失守等于全部设备失守——只绑 VPN 内网、强口令+双因素、及时升级、定期备份配置。
3. **凭据方案待选**：参考 [机密存储候选](<../../技术候选/机密存储工具.md>)；本轮检查时工作区已无 vault.py，不再以其为既有依赖。真实密钥和口令不进入调研文档或代码。
4. **审计与撤销设计**：后续方案需说明操作如何追溯、设备授权如何撤销；原运行规程已移除，不能作为已部署的审计机制。具体方式随所选平台与用户指定范围设计。
5. **操作范围待定**：完整设备控制是目标能力；哪些设备、数据与操作纳入一次任务，应在对应设计和实验计划中写清，不沿用旧报告的全局授权或排除清单。
