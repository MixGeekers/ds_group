# Ombre Brain 能否作为识雨内层组件

日期：2026-11-01（America/Caracas）。问题来自用户对 v1.0 的追问：为什么不直接复用 Ombre，同时承接情绪与记忆？证据为**本轮官方仓库与限定源码静态复核**，未安装、未运行、未做效果或成本对照，不是完整安全审计。

## 1. 结论与对前版的修正

**Ombre 有充分理由进入优先复用对照，不能仅因它不符合助手提出的单库设计而排除。** 它已经提供情感记忆、混合检索、衰减与浮现、感受记录、回顾和自我认知候选；这些明显减少需要自行实现的产品机制。它是否比 SQLite/FTS5 领域层更省工程量、更符合体验，尚无同场景实验结果。

前版将它降为“只参考、等待上游改变”，依据不足：我们没有比较受控接入或小范围修改的成本。单一 SQLite、六部分同库事务、FTS5 起步、情绪只调节表达和具体三维向量，均是助手提出的验证选择，不是用户限定。用户已经确定的是 A 插件内核心、内外双层、六部分逻辑职责、core / worker / replyer、外层对内部只读与双工通信。

一个受控记忆服务可以同时承接多个逻辑模块；六部分不要求六套实现。Ombre 作为存储与记忆服务运行，也不自动把 A 变成独立核心 B。是否需要独立的短时情绪状态，应按产品需求判断，不用本方案额外增加的 ToneView 要求否定现成组件。

**当前状态：已初评、优先对照验证；未采用、未接入。** SQLite/FTS5 保留为现有对照基线；公共契约尚未静默改成跨服务提交协议。

## 3. 两种情绪语义必须分清

Ombre 主要解决“这件经历带着什么情绪、为什么更容易想起、留下什么感受”；v1.0 的 ToneView 解决“当前会话的短时表达状态如何受限变化”。二者可以组合，也可以只保留前者。若识雨需要情绪影响记忆显著性，Ombre 比当前仅调节表达的基线更贴近该目标。

I 的自我认识可以承接认知与人格候选，但不等于版本化 PersonaProfile 的全部发布规则。plan 可以保存承诺，不代替授权、设备执行、任务效果核验与故障恢复。关系自动建立在当前 README 中仍标为未接线，不把已有关系展示说成完整关系学习。

## 4. 优先比较的接入方式

建议先比较**受控复用现成 Ombre 服务**，再考虑只抽取局部算法。重写情绪评分、检索和回顾机制不应成为默认起点。

1. DSH 插件中的 core 保持唯一决策与授权入口；一个薄 MemoryAdapter 持有 Ombre 连接，内部整理任务可调用 hold/grow/trace/dream/I。不把全套 MCP 工具自动注册给 replyer。
2. replyer 只取得经过范围裁剪的 MemoryView。按单个方法验证读取副作用；dream 记录见证，属于内部写操作，不能仅因名称像查询就开放给外层。
3. 首个对照只启用记忆、情绪记忆和回顾；You/them、公开 Tunnel、GitHub 同步及自动更新不作为起步依赖。服务原有打标/embedding 外发另纳入供应商、数据范围和费用配置。
4. 若最终由 Ombre 持有记忆主副本，识雨任务库保存命令、状态和稳定引用，不再维护第二份可独立修改的同义记忆。不能将跨服务调用写成“同一 SQLite 事务”。
5. 对跨服务写入验证幂等键、提交回执、期望版本、崩溃窗口和恢复核对。现有公开工具是否足够，或需增加小范围接口，仍须实验确认。适配失败不能通过放弃外层只读来补偿。
6. 分别核算真实清除、来源回读、用户审阅和状态版本的补齐成本。若需长期大面积 fork，才与现有领域层方案比较维护成本；不是一发现差异就直接重写整套系统。

Dashboard、Obsidian 直接编辑也是写路径，必须纳入可信用户控制、变更检测与版本冲突处理；仅限制模型的 MCP 工具表不能收口所有修改。breath 总入口还有活动记录及确保衰减引擎启动的动作，已核查的“不 touch”不能扩张为整个请求绝无附带活动，见[入口 L130–146](<https://github.com/P0luz/Ombre-Brain/blob/115d831d979bf67efc7150f976e2cb34c333c935/src/tools/breath/__init__.py#L130-L146>)。这些是需要明确所有者的适配点，不是拒选证据。

自然衰减和候选见证是服务内的领域写入；接入后应由明确政策委派并可观测，不能假称所有状态仍只由原 CoreCommitService 的单库事务改变。选择服务方案时需显式修订所有者、快照与恢复契约，再实现。
