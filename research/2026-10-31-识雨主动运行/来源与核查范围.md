## 关键核查与限制

1. **插件可以承载主动机制：**官方架构提供服务、事件、工具、会话及持久化扩展点。Schedule 在 Host 进程内运行；关闭进程后须等恢复才继续。它不是已经建成的识雨持续目标与任务系统。
2. **提醒投递不等于工作完成：**上游文档明确回执仅确认入箱持久化，两个存储提交间可能重复；用户指南还说明关闭 Host 对待消费 inbox 的处置。故识雨需要自己的任务生命周期和执行核验，不能只拿提醒列表当完成账本。
3. **MCP 已有实现证据：**本轮阅读配置、激活、重连接入和卸载路径，修正旧多机候选“DSH 是否支持 MCP 未确认”的上游能力判断。本机实际配置与服务连通性仍未验证。
4. **自愈边界：**sanitizeProfile 要求停止 profile 并排除并发写入，动作是备份 patch 与重设 bundle 列表；不是任意数据恢复或自主修复能力。进程外监督建议属于本轮架构推论。
5. **本地空间和外发分开：**上游 base 配置与组件文档支持会话日志默认贡献的结论；本机运行配置未读，不能推断正在上传。模型 API、额外日志贡献、反馈遥测是不同路径。
6. **上游文档存在需复核的交叉表述：**docs/user/guide/schedule.md 与 schedule 源码描述 Host 任务可恢复 Session；apps/desktop/README.md 的退出章节仍出现只在已加载 Session 中执行提醒的表述。本轮不据此宣布某个已安装 Desktop 版本的默认调度行为；后续应以固定版本的实际组合与实验核对。
7. **版本不同：**本机应用元数据 0.2.1-rc.5 与审阅快照中 base 包 0.2.2-alpha.2 不同。本文谈的是当前设计可参考的上游能力，不是本机所有能力已通过验收。
