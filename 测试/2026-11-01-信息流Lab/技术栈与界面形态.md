# Lab 技术栈与界面形态

日期：2026-11-01。**选型建议，待讨论；未实现、未安装、未运行。** 本轮回答“采用什么技术栈、是否有UI、Web还是DSH插件”。承接[Lab架构](<Lab架构.md>)，不因界面规划开始开发平台。

## 1. 推荐组合

**独立 Lab 服务＋Web UI＋DSH 薄适配插件；可选 DSH 内的 Lab 入口。**

Web是界面的呈现方式，插件是与宿主集成的方式，可以组合。识雨本身继续按A方案运行于DSH插件内；Lab的实验驱动、独立世界账本和评分管理放在被测宿主之外。关闭浏览器不应停止实验；被测DSH退出时Lab仍能记录退出、观察未知效果和发起获准的恢复实验。

| 形态 | 收益 | 限制与适用范围 |
|---|---|---|
| CLI＋现成报告页 | 接入最少，适合最早的协议验证与批量评测 | 多人消息、状态与效果的因果链不够直观；可作为无UI运行入口 |
| 独立Web Lab | 运行控制和证据不随被测DSH退出；能接不同模型/组件；前后端职责清楚 | 需要一个小型API服务和领域视图；本轮推荐主形态 |
| 全部放入被测DSH的插件 | 宿主内入口方便，可复用模型、会话和UI机制 | 杀宿主会同时失去驱动/观察，无法独立验证故障；不适合作为完整Lab的唯一运行位置 |
| 独立Lab＋DSH入口/桥接插件 | 保留宿主内使用体验，实验引擎独立；同一协议支持浏览器和插件入口 | 需核对插件UI/认证/生命周期兼容；属于推荐的后续集成方式 |
| 单独管理DSH实例承载Lab，再测另一个DSH | 也可以隔离被测宿主故障 | 两套宿主/profile更复杂；若用户希望所有操作在DSH内，可作为备选，仍要隔离观察与答案 |

这里的“独立”是本机按需启动的进程，不意味着云部署、常驻系统服务或分布式平台。Lab服务进程本身失效也要记录运行未完成，不能把独立进程说成高可用。

## 2. 推荐技术栈

| 部分 | 建议 | 理由与范围 |
|---|---|---|
| 主语言 | TypeScript | 连接现有DSH/队列/控制适配路线，UI与运行协议共用类型；接口仍做运行时校验 |
| Lab运行服务 | Node.js＋Fastify | 受限运行API、证据查询、运行列表；Node版本沿项目验证基线并核对实际依赖兼容，不直接追latest |
| Web UI | React＋TypeScript＋Vite | 浏览器SPA，围绕运行时间线与评审；与既有DSH工作台React方向相符；当前无SSR/SEO需求 |
| UI通信 | HTTP查询/命令＋SSE运行动态 | 控制请求与只读动态分开；SSE按序号断线续读，缺口转快照补齐；不把在线事件流当持久权威 |
| 场景与封存证据 | Markdown审阅稿＋JSON/JSONL＋文件产物 | 沿现有样本与证据包；附件/日志按引用查看，不把所有正文塞进UI内存 |
| 运行目录与查询索引 | SQLite用于run元数据/索引，原始证据独立文件 | Lab库与被测控制库分开；遵守项目既有SQLite验证门槛。最早单次探针可先用manifest文件，UI多运行管理时再落库 |
| 模型评测与Agent评分 | Promptfoo＋既定provider/agent-rubric或外部Judge接缝 | 复用比较、断言、Agent评分及报告；保留完整ReviewResult与独立事实报告 |
| 协议与业务时钟 | Node内置测试工具、MockTimers及显式Clock接缝 | 按既有架构区分虚拟语义时间与实际性能时间 |
| 持续流负载 | 有测试入口后按需k6 | 外生流独立到达；角色身份来自fixture，不从VU推断 |
| DSH接入 | 固定版本的薄测试桥；可选独立UI入口插件 | 输入注入、状态/事件导出、测试生命周期；业务决策仍由被测识雨执行 |

Fastify仅提供API，不接管识雨任务引擎；SQLite只保存Lab运行管理数据，不成为第二份识雨记忆。后续若同进程同步数据库操作影响注入/控制时延，使用受限存储线程或隔离索引写入，实际测量该开销。前端组件库与图表库先不固定，避免因画几个视图扩出第二套设计系统。

## 3. UI 应该能看什么

建议规划五个视图，先做领域核心，通用评测展示复用现成工具。

| 视图 | 使用者要解决的问题 |
|---|---|
| 场景与实验配置 | 选择S/FL故事、负责人已回应/未回应、噪音比例、合同B0/R1、被测对象、Judge和预算；显示本次冻结版本 |
| 运行时间线 | 左侧人物/会话，中间聊天与实际发送，旁侧事件和任务；能看到供应商说了什么、负责人何时回应、识雨何时静默或@ |
| 状态与效果 | 查看记忆/任务/授权变化及实际回执，区分已受理、已保存、已发送、unknown；点击回到来源 |
| 评审 | 程序断言、Agent逐项理由与证据、人工注释及分歧；不能修改历史运行事实 |
| 对比 | 两个模型/策略/版本在相同场景中的业务达成、打扰、公平、延迟、费用；标出条件不同或证据不足 |

运行中默认显示实际已发生内容。观察者可以查看隐藏世界/预期，但要与“识雨当时可见”视角显式区分；评审页面不把未来信息偷偷混入当时决策判断。隐藏oracle由后端按评审权限读取，不编进通用前端静态包或给被测Agent开放整个Lab浏览入口。

控制按钮区分“停止新增注入”“请求排空并结束实验”“故障注入终止被测进程”。业务虚拟时钟暂停不等于真实模型、外部调用或Task已停止；界面分别显示请求与实际确认。命令带runId、预期版本和幂等键，防双击/重连重复开跑。

评分Agent可以从封存运行启动重评，形成新reviewId；人工意见另存新标注版本，不覆盖原Agent意见或事实断言。

## 4. DSH 插件具体负责什么

**被测DSH内的测试桥**只在独立实验profile装载：把规范事件送入实际入口、把获准观测发送到Lab、响应测试生命周期请求。它不载入评分oracle、不替代core判断、任务调度或权限校验。被测宿主意外退出时桥也会退出，独立Lab据此继续处理实验状态。

**操作侧的可选入口插件**负责打开Lab、显示摘要或呈现相同领域组件。最小可先打开独立Web地址；内嵌面板/路由代理需核对宿主CSP、认证与模块加载，不假设任意iframe天然可用。UI被放在DSH里，并不要求Lab引擎也放进去。

前端复用以领域组件和API client为主：独立Vite构建可以打包自己的React，DSH版本可能需要使用宿主React/模块表；不能直接把同一bundle塞入宿主或加载第二份React而假设兼容。

已有plugins/shiyu-workbench仅作只读机制参考，保持源码、安装引用和功能原样。Lab不是在现有资料工作台中悄悄扩展一套实验管理系统。

本轮静态核对了[包清单](<../../plugins/shiyu-workbench/package.json>)中的Web client配置、[客户端](<../../plugins/shiyu-workbench/client.js>)的宿主React模块表/侧栏与面板注册，以及[Host插件](<../../plugins/shiyu-workbench/index.js>)的Connection精确路由与effect生命周期。它们证明已有可参考接缝，不证明Lab已接入或跨版本兼容。

## 5. 最小实现顺序

1. **先有可运行的实验接缝。** CLI/Node测试完成最小L2协议及证据封存；模型比较直接利用Promptfoo现成Web viewer。
2. **补薄Web UI。** 首先做运行列表/配置与单次运行时间线，其余证据通过引用查看；评分对比先连接现有结果页，不复制全部功能。
3. **加入领域评审与比较。** 聚合事实报告、Judge证据、人工分歧与成本分账，仍使用同一实验API。
4. **按使用习惯接DSH入口。** 浏览器继续可用，宿主退出时可以在独立界面检查实验；插件兼容单独验证。

这补充此前“首轮不建独立控制台”的范围：最早探针仍优先复用报告页；用户现要求讨论UI后，目标形态建议包含薄Web界面。尚未确定UI实施任务，也未启动页面开发。
